# 用户标签操作与验收手册

本文面向运营后台使用者、测试和运维人员，说明用户标签工作流的启停、触发、观察、验收和恢复边界。当前版本提供的是可运行的通用工作流骨架：任务注册、DAG、分片、运行期表、全量结果表切换、事件 outbox 与租约能力已经接通，但具体标签规则、业务事实采集和正式结果写入尚未实现。

> 业务计算阶段实现前，所有主工作流必须使用 `dryRun=true`。服务端会在入队前或业务阶段执行前拒绝非 dry-run 请求；工作流成功只证明框架链路可用，不证明生成了标签结果。

实现职责、表结构和扩展约束见[用户标签架构与扩展指南](功能模块/用户标签/用户标签实现与调度说明.md)，字段级接口契约见[用户标签接口总览](接口文档/用户标签/用户标签接口.md)，故障处置见[任务系统与用户标签故障处置手册](功能模块/用户标签/任务系统与用户标签排障手册.md)。

## 1. 当前能力与非目标

### 1.1 已具备

- `user_tag` 任务插件、四类主工作流和两个维护工作流的注册。
- `prepare -> collect_scope -> evaluate_tags -> resolve_changes -> persist_results -> finalize -> dispatch_hooks` DAG 状态推进。
- full 模式的互斥租约、临时结果表准备和 finalize 提交边界。
- UID 固定逻辑桶、工作流分片和运行期 UID/checkpoint 表。
- 标签 gain/lost 事件 outbox、失败重试和超时 `running` 回收。
- 管理后台手工触发、工作流查询和租约精确释放入口。

### 1.2 尚未具备

- 登录、充值、投注、返水等业务事实来源的读取。
- 标签定义、规则表达式、规则版本和依赖管理。
- 正式标签评估、差异计算和结果写入。
- 业务结果抽样、口径核对和正式上线验收。

因此，本手册的“通过”只表示骨架注册、调度、状态、表和锁边界通过，不得写成“用户标签功能已上线”。

## 2. 启用条件

### 2.1 配置

| 配置 | 作用 | 当前建议 |
| --- | --- | --- |
| `workflows.user_tag.enabled` | 注册用户标签插件、工作流和 handler | 仅在需要执行本手册骨架注册、调度或状态验收，且 Worker 已计划重启以完成插件注册时开启；业务评估、结果写入和 hook 消费未闭环前，生产保持关闭 |
| `workflows.user_tag.event_hook_enabled` | 允许派发 gain/lost hook | 没有真实 hook 消费者时保持关闭 |
| `default_shard_total` | 主工作流默认任务分片数 | 小数据从 `1` 开始，扩容前评估 DB 压力 |
| `default_batch_size` | 默认游标批次大小 | 默认 `2000` |
| `default_worker_count` | 节点内部并发 | 默认 `4`，当前骨架阶段不应盲目提高 |
| `diff_batch_size` | 差异处理批次 | 默认 `10000` |
| `event_batch_size` | outbox 单批派发量 | 默认 `500` |

工作流注册属于启动期能力；修改 `workflows.user_tag.enabled` 或 DAG 定义后必须重启包含 Worker 的进程。周期项由 `task_periodic` active release 管理时，应先发布配置再观察 Scheduler 同步状态。

### 2.2 运行角色

- 至少一个 Worker 监听 `maintenance` 队列。
- 周期触发还需要包含 Scheduler 位的进程，推荐控制面 `run_mode=5`。
- API、Worker、Scheduler 必须使用相同 `app_id`、任务 Redis 和代码版本。

### 2.3 数据库资产

新环境验证前应按[数据库初始化与变更交付治理](角色文档/运维/数据库迁移治理.md)完成空库初始化；已有环境则确认 DBA/运维变更单已创建并校验以下结构：

- `internal/database/assets/user_tag_0.sql`
- `internal/database/assets/user_tag_0_tmp.sql`
- `internal/database/assets/user_tag_runtime_uid.sql`
- `internal/database/assets/user_tag_runtime_checkpoint.sql`
- `internal/database/assets/user_tag_event_outbox.sql`

主线应用统一访问逻辑结果表 `user_tag`；历史源基线为 `user_tag_0`。候选分表分支的物理表和 Proxy 规则以同名分支文档为准，不能把主线表名直接套用到其它路由方案。

## 3. 工作流清单

| 工作流 | 模式 | 输入要求 | 当前行为 |
| --- | --- | --- | --- |
| `user_tag.full.rebuild` | `full` | 禁止 `uids`、`tagTypes`；必须 `dryRun=true` | 持有全局写租约，走完整 DAG，准备并提交全量临时结果表边界 |
| `user_tag.delta.refresh` | `delta` | `tagTypes` 可选；必须 `dryRun=true` | 复用主 DAG，不持有 full 全局写租约 |
| `user_tag.targeted.calc` | `targeted` | 必须提供 `uids`、`tagTypes`；必须 `dryRun=true` | 指定 UID 骨架验证，不按 workflow shard 拆分 |
| `user_tag.tag.recalculate` | `recalculate` | 必须提供 `tagTypes`；必须 `dryRun=true` | 指定标签类型的全量骨架链路 |
| `user_tag.runtime.cleanup` | 维护 | 无业务参数 | 清理过期运行期 UID 和 checkpoint 数据 |
| `user_tag.event_outbox.retry_scan` | 维护 | 无业务参数 | 回收超时 `running` 并重派 `pending/retry` 事件 |

四类主工作流共享以下 DAG：

```text
prepare
  -> collect_scope
  -> evaluate_tags
  -> resolve_changes
  -> persist_results
  -> finalize
  -> dispatch_hooks
```

`collect_scope`、`evaluate_tags`、`resolve_changes`、`persist_results` 当前在 dry-run 下返回跳过结果。节点显示成功或 `Skipped=true` 是预期，不代表标签规则已经执行。

## 4. 触发方式

### 4.1 通用工作流入口

使用 `POST /api/user-tags/workflows`。推荐先验证 `targeted`，再验证 `delta`，最后验证具有切表与租约边界的 `full`。

```json
{
  "mode": "targeted",
  "tagTypes": [1, 2],
  "uids": ["10001", "10002"],
  "queue": "maintenance",
  "shardTotal": 1,
  "batchSize": 500,
  "workerCount": 2,
  "dryRun": true,
  "uniqueKey": "user_tag:targeted:acceptance:20260811",
  "uniqueTTLSeconds": 1800,
  "timeoutSeconds": 1800
}
```

UID 必须使用十进制字符串，避免浏览器或 JavaScript 把大整数截断。服务端会对 UID 和标签类型去重、过滤非正数并排序，稳定生成默认去重指纹。

### 4.2 指定标签重算入口

`POST /api/user-tags/recalculations` 使用 snake_case 请求体，并转换为 `recalculate` 工作流：

```json
{
  "tag_types": [30, 31],
  "queue": "maintenance",
  "shard_total": 1,
  "batch_size": 2000,
  "worker_count": 4,
  "dry_run": true,
  "unique_ttl_seconds": 1800,
  "timeout_seconds": 1800
}
```

公网后台入口要求 JWT、权限和安全策略。服务间调用使用 `/internal/user-tags/workflows` 或 `/internal/user-tags/recalculations`，必须通过独立 `internal_server`、私网来源、Ops HMAC、Redis nonce 防重放，跨主机生产链路还必须使用 mTLS。

### 4.3 返回值记录

成功触发后立即记录：

- `taskId`：入口 trigger 任务。
- `workflowId`：本次工作流实例，后续查询、日志和租约操作都使用它。
- `workflowName`：实际匹配的工作流定义。
- `queue`：实际投递的逻辑队列。

接口成功只代表 trigger 已入队。至少要等工作流汇总进入成功或失败终态，才能形成验收结论。

## 5. 参数选择

| 参数 | 选择原则 | 风险 |
| --- | --- | --- |
| `queue` | 使用 Worker 已监听的 `maintenance` | 选错队列会长期 pending |
| `shardTotal` | 从 `1` 开始，小范围测量后再提高 | 分片越多并发查询和写入压力越高 |
| `batchSize` | 当前默认 `2000`，按单批耗时和 SQL 范围调整 | 过大增加锁、内存和超时风险 |
| `workerCount` | 当前默认 `4`，与 DB 连接池和下游容量匹配 | 与 workflow shard 并发相乘后可能放大压力 |
| `uniqueKey` | 手工验收使用可追溯业务键 | 重复使用会在 TTL 内抑制新请求 |
| `uniqueTTLSeconds` | 覆盖重复点击和预期执行窗口 | 过长会阻塞合法补跑，过短无法防重复 |
| `retry` | 只覆盖瞬时失败；正式阶段必须证明幂等 | 非幂等副作用可能被重复执行 |
| `timeoutSeconds` | 覆盖 trigger 任务，不替代节点显式超时 | 超时后外部副作用可能已经发生 |

`full` 是全站切表重建语义，不能携带 `uids` 或 `tagTypes`；指定 UID 使用 `targeted`，指定标签使用 `recalculate`。多维筛选 `filter_hash` 明确不能作为用户标签计算来源。

## 6. 标准验收流程

### 6.1 前置检查

1. 确认目标版本、`app_id`、任务 Redis 和数据库环境。
2. 在任务注册表确认六个 workflow name 和九个 task type 已注册。
3. 在任务队列确认 `maintenance` Worker 在线且没有异常积压。
4. 在运行配置确认用户标签周期项默认关闭或只包含 `dry_run=1`。
5. 核对五个数据库资产已执行，临时表和运行期表存在。
6. 确认 `event_hook_enabled` 与验收目标一致；没有 hook 时保持关闭。

### 6.2 targeted 骨架验收

1. 使用少量明确 UID 和标签类型触发 `targeted`。
2. 确认 trigger 从 pending 进入完成，工作流实例创建成功。
3. 确认七个节点按依赖顺序推进，主业务节点允许 `Skipped=true`。
4. 确认工作流进入成功终态，没有 unexpected retry/archived。
5. 确认没有正式标签结果变化，避免把骨架验证误当业务计算。

### 6.3 full 骨架验收

1. 确认没有其它 full 实例运行，再使用 `dryRun=true` 触发。
2. `prepare` 应清理当前 workflow 运行态并准备临时结果边界。
3. 四个通用业务阶段应成功跳过且不阻断 DAG。
4. `finalize` 应完成 full 提交边界；该节点禁用全局自动重试覆盖。
5. `dispatch_hooks` 按配置跳过或处理 outbox，并在最终分片后释放 full 租约。
6. 第一次工作流终态后再次触发一个新的 full dry-run，确认没有历史租约阻塞。

### 6.4 维护工作流验收

- 手工触发 `user_tag.runtime.cleanup`，确认只清理过期运行期数据，不删除正式结果。
- 手工触发 `user_tag.event_outbox.retry_scan`，确认会扫描全部 outbox 分片，超时 `running` 恢复为 `retry` 后按批次重派。
- 没有真实 outbox 事件时允许空跑成功；不得为了制造成功记录而手工修改生产事件状态。

## 7. 通过标准与证据

一次可审计验收至少保留：

| 证据 | 必须包含 |
| --- | --- |
| 配置快照 | 版本、`app_id`、`run_mode`、用户标签开关、active release |
| 触发请求 | 接口、请求体、操作者、时间和环境 |
| 任务回执 | `taskId`、`workflowId`、`workflowName`、`queue` |
| 工作流状态 | 七个节点及分片的开始、终态、错误和跳过原因 |
| 运行证据 | Worker/Scheduler 状态、Trace、结构化日志 |
| 数据证据 | 运行期表、临时表、outbox 与租约状态；明确正式结果未变化 |

当前版本满足以下条件才可判定“骨架验收通过”：

- 插件注册表包含 user-tag plugin，workflow registry 包含目标 full/delta/maintenance 名称，各节点 task type 都能解析到 handler；任一名称缺失或只存在源码未进入 registry 均不通过。
- trigger 入队成功，节点依赖顺序正确，工作流能进入终态。
- dry-run 通用阶段可以跳过，不产生正式标签结果。
- full 结束后没有遗留互斥租约，可再次触发。
- 维护工作流能独立执行，outbox 没有被错误标记成功。

验收报告必须写“用户标签骨架通过”，不能省略“骨架”二字。

## 8. 人工释放 full 租约

只有在以下条件全部成立时，才可调用 `POST /api/user-tags/workflow-lease/release`：

1. 原 workflow 已失败或明确终止。
2. 任务列表和 Worker 日志证明没有节点仍在运行。
3. 原流程不处于 `finalize` 切表或 `dispatch_hooks` 派发窗口。
4. 请求 `workflowId|mode` 与 Redis owner 精确匹配。
5. 已记录释放原因、操作者、MFA 票据和后续补偿方案。

租约释放接口只访问精确 key，不执行 `SCAN`。owner 不匹配时必须停止，不得删除 Redis key 或改 owner 绕过保护。若只是 archived 节点需要补跑，优先使用任务列表的立即执行能力，让工作流按原 DAG 继续推进。

## 9. 发布前检查

- 具体业务阶段未实现前，生产周期项保持 `enabled=false` 或固定 `dry_run=1`。
- 新增标签规则前先补规则来源、版本、索引、扫描范围、批次、幂等、回填与回滚方案。
- 启用事件 hook 前确认消费者已注册、幂等键为 `event_id`、失败会保留 outbox 重试状态。
- 调整分片或并发前先评估 `shardTotal × workerCount × Worker 实例数` 的最坏并发。
- full 正式写入开放前必须完成结果校验、切表原子性、旧表回退和异常租约恢复演练。
- 发布候选执行相关包测试、`go test ./...` 和 `git diff --check`。
