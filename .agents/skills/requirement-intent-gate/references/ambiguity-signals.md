# 需求歧义信号

## 可直接推进

先读源码后，以下情况通常无需追问：

- 用户给出准确仓库、文件、函数、route、SQL literal 或失败命令。
- 用户要求执行已定义且没有业务分叉的机械传播。
- 当前代码、测试或契约已唯一确定预期行为。
- 合理假设只影响表达方式，不改变外部行为、数据或风险边界。

推进前仍要说明非平凡任务的目标、证据、范围和验证。

## 必须暂停确认

- 使用“优化一下”“处理一下”“支持一下”“看下问题”等表述，但没有期望结果或受众。
- 同一句话可对应多个业务流程、角色、仓库、入口或数据对象。
- 请求混合排查与实现，现象尚未证明是缺陷。
- 日志、SQL、payload 或截图可能来自旧版本，且当前源码不能验证。
- 改动会改变资金、用户状态、权限、安全、API、共享 Redis Key、大表查询、任务调度、迁移或补偿。
- 需要破坏性操作、外部协调、新权限或明显扩大范围。

## 确认方式

1. 先说明已核对的源码事实和当前最可能理解。
2. 给出推荐的最小安全边界和明确非目标。
3. 只问一到三个会改变结果的问题，不泛泛要求用户“补充需求”。
