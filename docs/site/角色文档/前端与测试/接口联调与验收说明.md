## 联调建议

- 登录后先检查 `/api/auth/codes` 是否返回权限码
- 页面或按钮不显示时，优先核对前端权限常量和后端 `admin_permission.uuid` 是否一致
- 列表页异常时，优先核对筛选参数和分页参数
- 提交类接口联调时，保留请求体和响应体快照便于回归
- 用户标签页面联调优先按“操作与验收手册 -> 接口文档 -> 工作流状态”的顺序执行

## 稳定契约与联调注意事项

- 任务系统管理接口使用 `/api/tasks/*`；`/api/task/*` 不属于当前契约。前端 wrapper、route security manifest 和联调请求必须使用复数路径。
- 任务控制台里的“调度器状态总览 / 参数快照 / 时间轴”不走新接口，而是直接复用 `GET /api/tasks/queues` 返回的 `data.scheduler`；联调时不要误以为还缺一个单独的 scheduler API。
- “配置热加载”使用独立菜单；页面除了基础的 `enabled / watching / lastStatus` 外，还依赖 `restartRequired`、
  `restartReason`、`lastTriggerSource`、`lastFailureCategory`、`suppressedFailureCount` 这些字段；前端提示“需重启”时属于后端预期行为，不是渲染错误。
- 后台日志页使用统一日志字典 `route / action / describe / traceId / spanId / httpStatus / bizCode / latencyMs / success / errorMessage`；前端不得另建同义字段或把后端可变文案写死在常量中。
- `GET /api/live`、`GET /api/ready` 是公开探活接口，且访问日志默认被白名单屏蔽；探针访问后看不到 access log 属于预期，不应作为缺陷提单。
- 缓存管理页的 `GET /api/caches/keys` 在后端日志中输出 `request_source / search_path / provider_name / template_key / candidate_count / existing_count / latency_ms`；排查缓存搜索慢时，先按这些字段定位搜索来源、候选规模和实际命中，再结合接口耗时判断。
- 缓存搜索来源约定如下：页面手工检索=`manual_search`，业务页跳转自动定位=`route_jump`，模板键自动定位=`template_locate`，模板实例抽屉=`template_drawer`。

## 自动化契约与验证命令

- `internal/task/queue/manager_test.go:TestListQueuesReturnsSchedulerStatus` 约束 `GET /api/tasks/queues` 返回 `data.scheduler`，并校验同步间隔和心跳间隔等字段。
- `internal/bootstrap/app_reload_test.go:TestMarkHotReloadFailureSuppressesRepeatedLogs` 约束重复失败累计到 `suppressedFailureCount`；`internal/bootstrap/configload/reload_test.go:TestDetectReloadRestartImpact` 约束启动期配置变化返回 `restartRequired=true` 和具体原因。
- `internal/infra/loggerx/logger_test.go:TestFieldsFromMetaUsesUnifiedDictionary`、`TestTraceAttributesFromMetaUsesUnifiedChainFields` 约束日志字段与 Trace attribute 使用同一语义。
- `internal/handler/routes_test.go:TestDefaultRouteContractsSkipAccessLog` 约束 `/api/live`、`/api/ready`、`/api/metrics` 的路由规格跳过普通访问日志；`internal/middleware/access_log_test.go:TestSkipAccessLogMarksRequestMeta` 约束该规格写入请求元数据。
- 修改上述契约后运行：

```bash
go test ./internal/task/queue ./internal/bootstrap ./internal/bootstrap/configload ./internal/infra/loggerx ./internal/handler ./internal/middleware
```

- 只有最后一次修改后的命令退出码为 `0`，才能把对应自动化契约记为当前候选版本的验证证据；测试名称存在不能替代实际执行记录。
- 建议联调回归时按“任务总控台 -> 工作流状态 -> 配置热加载 -> 日志页 -> 健康检查”顺序做一轮页面核对，重点确认字段命名、状态提示和排障文案与接口返回一致。
- 排查缓存搜索慢的 Kibana 建议检索：
  - `message:"缓存搜索 完成" AND request_source:"manual_search"`
  - `message:"缓存搜索 完成" AND search_path:"template_candidates" AND template_key:"config_uuid:{uuid}"`
  - `message:"缓存搜索 失败" AND search_path:"unsupported_wildcard"`
  - `message:"缓存搜索 失败" AND route:"cache.search"`

## 用户标签联调

具体字段解释、模式填写方式和骨架验收口径已独立整理，避免在本页重复维护：

- 接口字段：见 [用户标签接口总览](接口文档/用户标签/用户标签接口.md)

### 指定标签骨架重算入口

- 接口：`POST /api/user-tags/recalculations`
- 请求体示例：

```json
{
  "tag_types": [1, 2]
}
```

- 预期结果：
  - admin 立即返回“已启动 N 个标签重算任务”
  - admin 走内网调用，admin 内部任务接收 `/internal/user-tags/recalculations`
  - admin 触发 `user_tag.tag.recalculate` 骨架工作流

### targeted 骨架入口

- 接口：`POST /api/user-tags/workflows`
- 请求体示例：

```json
{
  "mode": "targeted",
  "uids": ["10001", "10002"],
  "tagTypes": [1, 2],
  "dryRun": true
}
```

- 预期结果：
  - admin 返回 `taskId`、`workflowId`、`workflowName` 和 `queue`
  - 任务列表可看到 `prepare -> collect_scope -> ... -> dispatch_hooks`
  - 通用骨架节点默认跳过属于预期

## 鉴权与网络约束

- `GET /api/live`、`GET /api/ready` 为公开探活接口，不要求 JWT。
- 探针接口默认不打印 access log，联调时请以响应内容和状态码为准，不要用“日志是否出现”判断接口是否可用。
- admin 任务接口统一走 `/api/...`，要求 JWT。
- `admin 内部任务` 服务间调用统一走独立 `internal_server` 的 `/internal/...`，不带 JWT，但必须通过私网来源、Ops HMAC、Redis nonce 防重放；生产跨主机使用 mTLS。
