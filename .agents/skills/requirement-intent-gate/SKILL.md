# 需求意图闸门

## 执行流程

1. 判断最新请求属于分析、回答、实现、审查、验证还是交接，以用户最新明确要求为准。
2. 先收集可验证事实：生效的 `AGENTS.md`、项目规范、相关入口、调用链、配置、文档、测试、日志或用户提供的 payload。
3. 形成意图摘要：目标行为、当前行为、源码依据、拟改范围、明确非目标、验证计划和剩余歧义。
4. 仓库能低成本回答的问题先自行查证，只询问会实质改变结果的剩余歧义。
5. 当多个解释都合理，或改动会改变 API、数据、权限、安全、缓存兼容、迁移、补偿和用户可见流程时，编辑前只提出一个确认问题；问题必须包含源码已确认事实、分歧点和不同选择造成的结果，不重复询问仓库可查信息。
6. 用户要求“先分析”“先不改代码”或“只给方案”时，保持只读，直到用户明确切换为实现。
7. 边界确认后，把结论传递给主流程和对应专项 skill；无法可靠理解时停在编辑前，报告阻塞与猜测风险。

## 必须暂停编辑的条件

满足任一项且无法从当前仓库得到唯一答案时，先向用户提出一个只包含关键选择的确认问题：

- 同一措辞可对应不同仓库、角色、表、路由、任务入口或用户流程，选择不同会改变实现文件或外部行为。
- 用户只描述现象、日志、SQL、payload 或截图，没有说明期望终态；材料可能来自旧版本或其它环境，当前源码无法证明其仍然成立。
- 改动会新增、删除或改变 request/response、业务码、权限、RouteMeta、签名/加密、JWT/session、Redis Key 兼容、表结构、基线数据、回填、任务调度或前端可见流程。
- 存在破坏性写入、不可逆删除、数据迁移、缓存全量失效、停机、跨服务发布顺序或人工补偿，而用户未确认目标环境和恢复边界。
- 实现需要新增目录、框架、外部依赖或长期维护抽象，且现有实现和成熟方案之间的取舍会改变维护成本或交付范围。

以下情况可以继续，不应把闸门变成无意义询问：

- 文件、入口、默认值或调用方可以通过 `rg`、源码、测试和配置唯一确定。
- 假设只影响内部表达，不改变 API、数据、安全、权限、兼容、资源压力和用户可见行为；把假设记录在意图摘要中即可。
- 用户已经明确授权实现，剩余选择属于当前项目风格下可逆、局部且有现有模式支撑的实现细节。

## 确认问题质量

- 问题先写已确认事实和产生分歧的具体点，再给出会导致的不同结果；不能只问“请确认需求”或一次抛出大量仓库可查问题。
- 用户回答后更新目标、非目标、受影响入口、数据/契约变化和验证计划；若回答仍不能排除高风险分歧，继续只读查证，不擅自选一个解释。

## 意图摘要

```text
目标:
源码证据:
拟修改:
不修改:
仍不确定:
验证:
确认问题:
```

判断是否需要暂停确认时，读取 `references/ambiguity-signals.md`。
