# AI 开发规范

本文档是 AI 参与 `admin-go` 与 `admin-vue` 开发时的项目级质量标准，适用于功能实现、问题修复、重构、测试、配置、SQL、脚本和文档。目标是让 AI 交付与人工开发遵守同一套架构边界、工程风格和生产门槛。

## 使用方式

- 根目录 `AGENTS.md` 是短入口，负责声明不可跳过的流程、skill 和验证命令。
- [AI 开发提示词](角色文档/后端开发/AI开发提示词.md)是可复制的任务入口，只保留高频硬约束。
- 本文维护完整项目规范；遇到细分领域时，再读取对应专题文档和 skill reference。
- 用户最新明确要求优先，但不能绕过安全、数据完整性和诚实交付边界。

## 关键术语必须可验证

本规范允许使用“简洁”“清晰”“闭环”“同步”“必要时”“验证通过”“生产可用”等术语，但禁止把术语本身当作执行要求或完成证据。出现这些词时，必须同时写出检查对象、触发条件、通过标准和不满足时的处理方式；只有形容词、没有判定条件的句子视为无效规则。

### “完整”“闭环”“生产可用”

使用这些术语时，至少逐项确认并记录：

- 真实入口已经接通，包括路由、命令、Worker、Scheduler、注册表或运行时加载点；只有 helper、DTO、模板、页面外壳或测试构造不算入口。
- 主调用链已经从入口追到最终数据写入、外部请求、消息投递、文件输出或响应写出；每个新增分支都有调用方，成功和失败都能形成确定结果。
- 参数校验、权限与安全、事务、幂等、超时、取消、重试、并发上限和资源释放按实际故障模型处理；不适用项必须说明为什么不适用。
- API、配置、数据库、Redis、SQL/Lua、业务码、i18n、前端、文档、测试和运维交接已逐面检查；不能用“已同步相关内容”替代清单。
- 最后一次修改后已有可复现验证。受环境阻塞的路径必须标记未验证，并说明影响、替代证据和上线前责任人，不能写成“生产可用”。

### “简洁”“清晰”“易读”“易维护”

这些词必须落实为代码结构判断：

- 每个新增目录、接口、结构体、状态、分支、wrapper 和 helper 都能指出当前需求、真实调用方、稳定复用边界或故障证据；仅为“以后可能复用/替换”而增加的层级不得保留。
- 主流程能够沿业务顺序阅读；只转发参数且不承担校验、转换、事务、重试、隔离外部依赖等职责的包装应内联，连续跳转不能掩盖真实副作用。
- 相同业务规则只保留一个权威实现；重复判断、魔法字符串、catch-all `Manager/Helper/Common`、职责与名称不符的对象必须合并、重命名或删除。
- 锁、租约、幂等、CAS、事务、超时、取消和状态机如果保护真实并发或故障窗口，属于正确性边界，不能为了减少代码行数删除。
- 清理现有代码或文件时必须先分类：能从真实入口到达最终副作用的是“生产已启用”；没有当前业务调用方、但仍承载稳定扩展契约、已有多实现、外部依赖隔离、跨服务共享约定、CLI/Make/测试/部署/运维入口或明确职责与聚焦测试的是“基础能力但当前未启用”；只有所有入口与独立职责均消失、已有权威替代且删除不损失能力或兼容边界的才是“确认废弃无用”。不得仅凭 `rg` 没搜到业务调用方删除基础能力。
- 注释说明代码无法自行表达的业务意图、数据来源、单位、边界或风险；重复函数名、逐行翻译代码和“处理数据”“优化逻辑”不算有效注释。

### “小而聚焦”“保持兼容”“不改变语义”

- 每个修改文件和关键 diff 都必须能映射到已确认需求、必要同步面或验证修复；无映射的重命名、格式化、目录调整和顺手重构应移出本任务。
- “保持兼容”必须列出需要保持的请求字段、响应字段、业务码、权限、安全策略、配置键、数据库/Redis 数据形状、错误、时序和副作用；不能只比较函数签名。
- 需要改变外部行为时，必须明确旧行为、新行为、调用方、兼容窗口、发布顺序和清理条件，不能一边写“保持兼容”一边静默改变契约。

### “同步”“相关”“按需”“必要时”

- “同步”先以源码 diff 和调用方搜索识别触发面。route、request/response、RouteMeta、权限码、审计动作、安全字段、业务码、i18n、前端 wrapper/type、配置样例、Model、初始化 DDL/DML、Redis Key、SQL/Lua、测试、文档和运维步骤是发现清单，不是要求每项都产生文件的固定表单；每个触发面必须记录源码依据、修改文件和验证结果。只有常见风险面容易被误判为已处理时才写不适用及具体依据，禁止用一个汇总“不适用”覆盖未检查项。
- “相关文件”“相关测试”“按需处理”不能单独作为指令；必须给出发现方式或触发条件，例如“修改共享查询 helper 时运行所有调用包测试”“改变可见交互时补浏览器冒烟”。
- “必要时”后必须紧跟可判断条件、执行动作和证据。无法写出触发条件时，应删除该词并明确选择，或在实现前向开发确认。

### “高性能”“安全”“风险可控”

- 性能结论必须绑定热路径、调用频率、数据规模、索引/执行计划、扫描行数、返回行数、I/O 次数、batch、timeout、concurrency 和压测或基准证据；没有前后数据时只能说明完成了风险控制，不能宣称“性能已优化”。
- 安全结论必须列出身份来源、鉴权、权限、输入边界、敏感字段、密钥/随机数来源、重放防护、日志脱敏和失败业务码；通过正常请求测试不能证明安全路径完整。
- 风险说明必须包含触发条件、影响对象、监控指标、停止条件、恢复或补偿动作和责任边界；“风险较低”“可控”不能作为上线依据。

### “验证通过”“已完成”

- 验证记录必须包含最后一次修改后的完整命令、执行目录、范围、退出结果和未覆盖路径；旧快照、只测 helper、只看编译或只运行 happy path 不能证明整项需求完成。
- 文档改动至少检查相对链接、导航、权限资源、命令和路径；Skill 改动还要检查 frontmatter、触发描述、引用资源和两个仓库的一致性。
- 最终交付必须把状态明确分成已完成且已验证、已完成但未验证、已跳过、被阻塞、交付待人工执行，禁止只写“已完成”“测试正常”或“问题已解决”。

编写新规则时优先使用“当 `<可观察触发条件>` 成立，检查 `<明确对象>`，执行 `<具体动作>`，以 `<命令/状态/输出>` 为通过证据；禁止 `<可识别的错误做法>`”的句式。README 可以保留导航摘要，Skill 的执行步骤、AI 开发规范和验收清单不得用摘要替代上述判定细节。

## 1. 总原则

- 先读现有代码和文档，再改代码；不能只凭通用经验生成实现。
- 所有非平凡任务必须按标准开发执行流程推进：意图确认、源码证据、边界说明、实现、同步面检查、验证、交付复核。
- 需求或问题表述不充分、存在多种解释、目标仓库/入口不清或涉及接口、数据、权限、安全、大表、缓存、迁移时，必须先结合代码和文档说明理解、证据、待确认点和执行边界；未经确认不得直接落代码。
- 优先延续当前项目模式和现有分层；遇到成熟通用能力、高风险基础设施或手写实现容易出错的场景，必须先检查现有实现和成熟依赖/框架。确需新增抽象、目录、框架或依赖时，先说明必要性、收益、替代方案、影响范围和验证方式，并让开发确认后再落地。
- 每个新增目录、接口、结构体、状态、分支、wrapper 和 helper 必须满足本页“简洁/清晰/易维护”的判定清单；没有当前需求、真实调用方、稳定复用边界或故障证据的抽象不得保留，只转发参数且无独立职责的包装应内联。
- 性能改动先记录热路径、调用频率、数据规模、DB/Redis/MQ 往返、扫描/返回上限、分配、batch、timeout 和 concurrency；没有执行计划、trace、基准或前后指标时，只能说明减少的具体 I/O/扫描/分配，不能宣称性能已提升。
- 每个 helper、interface、wrapper、状态和分支都必须解决当前已证明的问题。未上线兼容逻辑只有经三分类确认没有静态/运行时/外部调用方、不承载基础扩展或共享契约，且删除不损失测试、部署和运维能力时才删除；租约、幂等和原子状态迁移等真实并发边界保持最小且可测试。
- 代码、配置和文档说明至少提供一项代码本身无法表达的信息：业务原因、数据来源、单位、空值、上限、顺序、并发、失败策略、兼容窗口或运维风险；逐字复述标识符、“处理数据/优化逻辑/异常兜底”和与实现不一致的说明均不合格。
- 重构必须保证原有能力不遗漏，并说明迁移后的入口、影响范围和验证方式。
- 需求任务及其拆解出的每个小任务必须按真实入口、调用链和交付面闭环完成；禁止只搭骨架、只写样例、只实现基础能力、单一分支或 happy path 后宣称完成。确因依赖、权限、环境或风险无法完成时，必须在交付说明中明确未完成项、阻塞原因、影响范围和下一步处理方式。
- 文档、接口、测试和配置必须与代码同步；发现旧文档与代码不一致时要一并修正。
- 配置热加载必须区分运行参数和启动期注册开关；handler、workflow、任务插件、组件注册和基础设施连接不在线补注册或重建，变更后必须通过 `restartRequired/restartReason` 暴露重启原因。

## 2. 命名要求

- 命名必须短而准确，贴合当前领域语境；禁止随意取名、过度缩写或堆很长的描述性名字。
- 目录、变量、方法、常量、结构体、接口和字段命名必须与当前职责一致；实现职责变化后必须同步改名，禁止沿用旧名、泛名、错名或过长说明式命名。
- Go 包名短小、全小写，不使用下划线。
- 方法名使用“动词 + 对象/结果”表达行为，例如 `BuildPayload`、`SyncPeriodicTasks`；私有 helper 只覆盖当前意图，避免 `handleData`、`doProcess` 这类泛名。
- 变量名按作用域控制长度：短作用域可用 `ctx`、`err`、`tx`、`db`、`uid`、`rows`；跨多段逻辑的变量必须写清领域含义。
- 结构体使用名词或领域对象命名；请求以 `Req` 结尾，响应以 `Resp` 结尾，列表项以 `Item` 结尾。
- 接口按能力命名，优先使用 `Reader`、`Writer`、`Repository`、`Provider` 等自然后缀；只有一个实现且无替换点时不要强行抽接口。
- 新增抽象前必须确认真实替换点、稳定复用边界和维护成本；新增接口、目录、wrapper 或 helper 必须满足至少一项：隔离外部依赖、解除真实依赖环、承载两个及以上现有实现、收口两个及以上调用方已稳定的同一业务规则，或删除主调用链中的重复状态转换。仅以“未来可能复用或替换”为理由不得抽象。
- 常量按领域前缀集中定义，名称表达稳定业务含义或枚举语义；禁止魔法字符串、随意数字和含糊的 `DefaultValue`。
- 切片、map 命名体现内容和单位，例如 `adminIDs`、`queueWeights`、`workflowByName`。
- 路由别名使用 `domain.resource.action`，例如 `task.workflow.trigger`。
- Redis Key 必须集中在 `common/rediskeys`，禁止业务代码临时拼接高基数通配 Key。
- 工作流和批处理链路统一使用 `workflowID`、`mode`、`node`、`shardIndex`、`shardTotal`、`uid` 等命名。

## 3. 注释要求

新增或重构以下内容必须补中文注释：变量、常量、方法、结构体、结构体字段、map 字段含义、路由、GORM Model、接口和方法内部关键逻辑。

顶层稳定契约中的 map、数组、切片等字段，必须说明元素 key/value 或元素对象含义、数据来源、边界条件、排序/去重和空值语义。

注释必须说明业务意图、数据来源、边界条件、性能保护点或降级策略。禁止重复代码本身，也禁止只写“优化”“兜底”“处理数据”这类含糊描述。一句话能说明白的不要写成长段。

### YAML 配置字段行级注释

项目自有的应用配置 YAML 是对开发、测试和运维公开的配置契约，不能只给父节点写一条概述。新增或修改配置结构、默认值、校验、加载来源或生效方式时，按以下规则维护 `etc/config*.sample.yaml`、外置运行期配置样例和项目自有部署配置模板：

- 每个由项目代码读取的固定字段必须在字段正上方放置中文 `#` 注释，注释缩进必须与字段一致；父 mapping、父 list 或章节标题的说明不能代替固定子字段的行级注释，行尾注释也不能作为唯一说明。
- 每条字段注释必须说明字段的消费组件或业务用途。源码对该字段定义了类型/数据形状、枚举、合法范围、单位、缺省值、空字符串、空集合、`0`、`false`、normalize/getter 回退、热加载应用器、重启要求、敏感信息来源/脱敏/轮换，或与其它字段的依赖、互斥、顺序关系时，注释必须把存在的行为逐项写出；源码没有定义的行为不得凭字段名猜测。
- mapping 或 list 父字段必须说明子项数据形状、唯一键或顺序是否有意义、空对象/空列表行为以及覆盖或合并规则。固定结构的每个子字段仍需单独注释；动态 map 的业务 key、地址映射或重复列表项，只在父字段已经明确 key/value 语义、约束和空值行为时，允许不为每条数据复制同一句注释。
- 密钥、密码、token、私钥、完整 DSN 等敏感字段只说明注入来源、是否允许为空、最小约束、轮换或重启边界；注释、样例、日志和交付记录均不得包含真实值。样例使用可识别占位值，本地实际配置从带注释样例复制，并在新增字段时保留对应说明。
- `docker-compose*.yml`、CI workflow、Prometheus rule 等由外部工具定义的 schema，纯数据清单以及生成文件不机械套用应用配置规则。排除时必须记录文件路径、schema 所有者、文件职责和项目代码不把其字段作为应用配置读取的依据；其中项目自定义的环境变量或嵌套应用配置仍需在所属模板处说明。
- 修改注释前先核对 config struct/tag、默认值、normalize/getter、校验器、实际消费方和 reload 应用器。无法从源码证明默认值或生效边界时，先补证据或向开发确认，禁止编造“默认即可”“支持热加载”“修改后重启”等结论。

通过标准：所有纳入范围的固定字段都有紧邻且同缩进的有效中文注释；YAML 解析和配置样例加载测试成功；字段名、默认值和 reload/restart 说明与最后一次修改后的源码一致；排除文件具有逐文件依据。只写“配置字段均有说明”或只检查 YAML 能解析，不算完成。

## 4. 数据库与缓存规范

- MySQL/SQL 编写必须优先使用 GORM 链式调用；读操作使用 `ReadDB`，写操作使用 `WriteDB`，事务内必须沿用同一个 `tx`，禁止参考遗留风格随意手写原生 SQL。
- 所有数据库表必须有对应 Model；新增表、改表、迁移 DDL 或修复 DDL 时，必须同步创建或更新 Model 的 `TableName`、字段类型、主键、索引/唯一约束、默认值、NULL 语义、软删除和时间字段，确保 Model 与 DDL 对齐。
- 只有 GORM 无法安全表达、动态 DDL/批量切表/ClickHouse 聚合等链式调用不适用，或链式调用会严重影响性能时才允许原生 SQL；使用前必须写清必要性、索引依据、预估扫描范围、分页/批量上限、超时/并发控制和 DB 压力。
- 所有新增或调整的 SQL 都必须先评估执行计划、索引、基数、返回行数和目标库压力；禁止用历史遗留 SQL 风格代替性能评估。
- 需要随应用或已产品化运维工具运行的原生 SQL 必须保存为稳定 `*.sql.tmpl` 资产并由真实调用方加载；禁止在 Go 业务代码中内联多行 SQL、`fmt.Sprintf("SELECT ...")` 或模板外 `Exec("RENAME TABLE ...")`。一次性 DBA 变更 SQL 不属于代码资产，按下述仓库外流程交付。
- `.lua` 是 `go:embed` 加载的 Redis Lua 脚本代码资产，必须提交仓库；禁止在 Go 业务代码中使用 `redis.NewScript(...)` 内联 Lua。
- 仓库内 DDL、DML 和 `defaultMigrationSpecs` 只用于全新空库初始化，不承担已部署环境的逐版本升级。表、字段、索引、约束或基线数据变化时，直接修改对应原始初始化资产，使新环境一次初始化得到当前完整状态。
- 禁止新增按需求、日期、工单或版本拆分的 `add_*`、`alter_*`、`sync_*`、`*_seed_*`、`*_repair_*`、`*_backfill_*` 等碎片化迁移 SQL，也不得向 `defaultMigrationSpecs` 追加日常变更版本。
- 存量库需要的增量 DDL/DML、回填、修复和补偿 SQL 只能生成到被 `.gitignore` 排除的 `data/sql-changes/<change-id>/`，通过发布工单或受控文件渠道交给 DBA/运维命令行执行；这些文件不得提交、暂存或登记到 `schema_migrations`。
- DBA 交付必须说明目标环境/实例/库/表、当前与目标版本、SQL SHA-256、执行顺序、索引和扫描边界、锁表风险、批量/超时/并发、备份、验证、停止条件及恢复方案。只给 SQL 文本不算完整交付。
- `schema_migrations` 只记录初始化资产。初始化 SQL 更新导致旧库 checksum 不同时，不得重放初始化基线、伪造登记或新增迁移掩盖差异；旧库一律走 DBA/运维增量变更流程。
- 文档权限采用双表基线：入口保留在 `admin_permission.sql`，单篇正文使用 `admin_doc_permission.sql` 的 `site + path`，角色关系使用 `admin_role_doc_permission_rel.sql`。新增或删除 Markdown 时同步 `internal/routealias/docs.go` 和文档导航；未上线阶段直接更新基线资产，不追加增量迁移。
- SQL seed 如果显式保留自增主键 `id`，新增行必须按 `id` 递增放在对应位置，不能为了贴近同类业务行插入到中间。
- 新增或移动 `*.sql.tmpl`、`.lua` 时，必须同步检查 Go 侧 `//go:embed`、渲染方法和最小单测。
- Go 调用侧必须使用 `embedasset.StripLeadingLineComments(template, "--")` 或当前包 helper 剥离文件头说明，再交给 MySQL、ClickHouse 或 Redis 执行。
- 不允许在业务接口中执行 Redis 全库 `SCAN` 或模板通配扫描；高基数缓存必须通过索引集合、精确 Key、白名单模板、登记模板或异步离线任务处理。
- 重构时优先复用现有 helper、模板渲染器、分页游标、去重和错误包装方法；同类逻辑重复时抽到当前包公共 helper。

`*.sql.tmpl` 文件头使用连续 SQL 行注释，只记录用途、方言、调用方、参数来源和安全边界；同一信息不得在多行重复：

```sql
-- 代码资产：说明该 SQL 模板解决什么问题。
-- SQL 方言：MySQL / ClickHouse / ANSI SQL；使用窗口函数、JSON、在线 DDL 或版本相关语法时写明最低版本和方言限制。
-- 调用方：说明 Go 侧函数或方法名，以及 go:embed 加载后会先剥离本说明再执行。
-- 参数来源：说明占位符、绑定参数、动态表名或条件片段来自哪里。
-- 安全边界：说明白名单、转义、参数绑定、批量上限、事务或幂等边界。
```

`.lua` 文件头使用连续 Lua 行注释；涉及删除、释放锁、续租等敏感操作必须写清 owner 比对或防误删策略：

```lua
-- 代码资产：说明该 Redis Lua 脚本解决什么问题。
-- 调用方：说明 Go 侧函数或方法名，以及 go:embed 加载后会先剥离本说明再发送 Redis。
-- KEYS[1]：说明 Redis Key 来源、所属 Redis Key 模板和是否高基数。
-- ARGV[1]：说明参数来源、类型和边界。
-- 原子性边界：说明脚本内原子操作范围、owner 校验、TTL 或幂等策略。
```

## 5. 错误处理规范

- 底层错误必须使用 `github.com/Is999/go-utils/errors` 的 `errors.Tag`、`errors.Wrap` 或 `errors.Wrapf` 包装。
- 同一个函数里，同一个 `error` 值只包装一次；跨函数边界可以继续包装，因为那是新的调用语义和上下文，避免裸错误漏出去。
- 业务中间层只返回错误，不打印 `error` 级日志；禁止在 logic、repository、service、model、helper 等内层随意调用 `loggerx.Errorw`、`loggerx.ErrorTextw` 或 `logx.Error*`。
- 顶层 handler、worker、scheduler 或不可返回错误的兜底协程统一打印 `error` 级日志；同一错误链路只能在最外层打印一次。
- 底层需要补排障信息时只能通过 `errors.Wrapf` 写入上下文字段，不能用多处 `error` 日志替代错误链。
- 错误上下文必须带可追踪字段，例如 `workflow_id`、`mode`、`node`、`shard`、`uid`、`task_id`、`event_id`。

```go
if err != nil {
    return errors.Wrapf(err, "工作流节点执行失败 workflow_id=%s mode=%s node=%s shard=%d/%d", workflowID, mode, node, shardIndex, shardTotal)
}
```

## 6. 日志规范

- 日志统一使用 `loggerx.Infow`、`loggerx.Debugw`、`loggerx.Errorw`。
- 正常流程只打印关键节点，不刷屏。
- `error` 级日志只在最外层打印一次；底层通过错误返回和错误包装保留上下文。
- 顶层结构化字段只保留公共检索维度，例如 `trace_id`、`route`、`user_id`、`http_status`、`biz_code`、`error`、`error_chain`、`task_id`、`workflow_id`、`mode`、`node`、`shard`；其它细节交给 `loggerx` 写入 `content`。
- 日志字段类型必须稳定；时间窗口和间隔细节使用带单位的字段名，例如 `window_start_unix`、`interval_seconds`。

```go
loggerx.Infow(ctx, "工作流节点开始处理",
    logx.Field("workflow_id", workflowID),
    logx.Field("mode", mode),
    logx.Field("node", node),
    logx.Field("shard", shardIndex),
)
```

## 7. 接口与业务码规范

- API 响应必须使用统一结构：`status/code/message/data/traceId/spanId`。
- 不同业务错误必须返回不同业务码；业务码要表达上下文和失败节点，但 `message` 不能暴露 SQL、密钥、内部表名或真实下游错误。
- 新增业务码必须补中文和英文文案。
- 新增接口必须补接口文档，文档格式遵循 [接口文档统一规范](接口文档/接口文档统一规范.md)。
- 新增路由必须补 `RouteMeta`、审计动作和中文说明；需要权限控制的路由必须补权限码。
- 路由别名被 `RouteMeta`、签名/加密策略、权限白名单、强制改密或 MFA 放行列表复用时，必须先收口到 `internal/routealias` 常量，禁止在多处重复写字符串。
- 内网路由必须使用 `/internal/` 前缀和 `RouteAccessInternal`，只注册到独立 `internal_server`；必须校验 Ops HMAC 与 Redis nonce 防重放，生产跨主机链路使用 mTLS。
- 健康探针或高频轮询接口如需跳过普通访问日志，必须在模块 `RouteSpecs()` 设置 `SkipAccessLog`，真实注册和 `RouteContract` 会从规格派生；禁止在访问日志中间件里追加路径白名单。
- 仅 token 白名单路由可不配置权限码，但必须写清白名单原因和 token 校验边界，例如个人收件箱能力、`/api/permissions/max-uuid`。
- 接口文档如果发现与代码不一致，必须同步修正，不能继续保留误导性描述。

## 8. 大数据查询与批处理规范

- 涉及大表、大结果集或高频查询时，必须先评估数据量、索引、执行计划、并发量和目标库压力，不能直接上线试跑。
- 在线接口禁止无上限全表查询、深分页 `OFFSET`、`SELECT *`、无索引排序/聚合/JOIN、一次性加载超大 ID 集合。
- 查询必须有明确边界，优先按时间窗口、主键游标、分片或状态分页推进；`batch_size`、最大批次数、超时、并发和 `sleep/backoff` 必须可控。
- 大聚合、历史回补、跨库对账、批量修复和导出应走后台任务、维护队列、汇总表、ClickHouse 或数仓，禁止放在 HTTP 请求内长时间执行。
- 批量写入和删除必须小批次按主键或索引推进，避免长事务、大锁、超大 `IN/NOT IN`；任务要支持幂等、断点续跑、进度水位和可中止。
- 只读且允许复制延迟的查询使用读库；跨期聚合、分析和对账使用 ClickHouse/数仓或离线链路；预估扫描/返回规模超过在线上限、执行时间超过请求 timeout 或并发可能耗尽连接池时，必须转队列/后台任务并设置限流、熔断或降级，不能继续放在 HTTP 热路径。
- 新增大数据查询必须补充索引依据、保护阈值、关键日志/指标和最小测试；无法验证执行计划时，要说明风险和上线观察方式。
- 管理后台列表不默认实时统计超大总数；确需统计时使用缓存、异步汇总或受控近似值，并在接口文档说明口径。

## 9. 前端联动规范

- 接口字段优先延续当前已发布契约；只有仓库中同时存在 snake_case/camelCase 调用方且不能同批升级时才保留双字段解析，并记录调用方、移除版本和防漂移测试，禁止为假设兼容长期维护别名。
- 敏感操作必须支持 MFA 二次票据。
- 加密、签名、秘钥版本配置变更后，必须同步更新前端配置说明和接口文档。
- RSA 私钥生成和下载只允许由前端本地完成，禁止新增后端生成私钥、下载私钥或返回私钥明文的接口。
- 前端展示错误优先使用后端业务码和国际化消息，不硬编码后端内部错误。

## 10. 文档质量

- 先明确受众和任务：README 面向首次接手者，开发规范面向实现与评审，接口文档面向调用方，运维手册面向发布和排障。
- 标题表达稳定主题或结论，步骤按真实执行顺序排列；文档超过两个二级章节时在侧边栏或正文目录提供可点击入口，同一规则正文只维护一份，其它入口写摘要并链接权威正文。
- 命令、路径、配置键、默认值、接口字段和示例必须能从当前仓库验证；不凭记忆复制兄弟仓库内容。
- 文档只描述当前代码和部署资产已支持的行为。计划、假设和未完成项必须明确标注，不能写成已上线能力。
- 不保留“最近一次测试通过”“当前没有问题”等会自然失效且缺少候选快照的状态性结论；验证结果写入具体交付记录。
- 修改 Markdown 时检查相对链接、导航、权限资源和文档站访问边界；新增或删除正文时同步文档权限资产和 `internal/routealias/docs.go`。
- 同一规则只保留一个权威正文，其它入口使用摘要和链接。摘要不得省略触发条件、禁止项和权威链接；正文必须按受众任务拆分标题、前置条件、步骤、验证和故障处理，禁止用连续长段落重复同一结论。

## 11. 质量门槛

AI 每次改动完成后必须运行对应测试；能跑全量时至少执行：

```bash
go test ./...
```

如果改动范围较小或受环境限制无法跑全量，也至少执行对应包测试，并说明未跑全量测试的原因。

提交前必须自查：

- 是否误删功能。
- 是否在需求或问题不清时先基于代码和文档确认意图、证据、待确认点和执行边界，而不是直接猜测实现。
- 是否逐项完成需求任务和拆解后的小任务，并明确说明完成状态。
- 是否存在只实现基础能力、只打样、未接入真实调用链或未验证却宣称完成的半成品。
- 是否复查目录、变量、方法、常量、结构体、接口和字段命名，确保短而准确且贴合当前职责。
- 是否先评估成熟依赖/现有实现；新增抽象、目录、框架或依赖是否已有开发确认。
- 是否存在未使用代码、重复抽象、过度封装，或因拒绝成熟依赖而手搓高风险基础能力。
- 是否优先使用 GORM 链式调用；原生 SQL 是否具备必要性说明和性能保护边界。
- 是否为所有新增或调整的表补齐 Model，并确认 Model 与 DDL 在表名、字段、类型、默认值、NULL、主键、索引和时间/软删除语义上对齐。
- 是否只更新完整初始化 DDL/DML，且没有新增碎片化迁移 SQL 或向 `defaultMigrationSpecs` 追加日常版本。
- 存量库本地 SQL 是否位于被忽略的 `data/sql-changes/<change-id>/`、未进入 Git，并具备 DBA/运维执行与恢复说明。
- 是否使用 `errors.Tag` 或 `errors.Wrapf`。
- 是否把 `error` 级日志留在 handler、worker、scheduler 等最外层。
- 是否让 `*.sql.tmpl`、`.lua` 文件头说明在执行前通过 `embedasset` 或当前包 helper 剥离。
- 新增或重构的变量、常量、方法、结构体/字段、map 字段、路由、GORM Model、接口和关键逻辑是否有中文注释，且注释是否给出业务原因、数据来源/单位、边界或风险，而非复述代码。
- 是否补接口文档、开发文档和必要测试。
