# 任务系统运行与操作手册

本文是 Admin 任务系统的权威运行手册，面向后端开发、测试和运维人员。内容覆盖 API、Worker、Scheduler、队列、工作流、周期调度、终态历史和故障恢复；字段级请求与响应以[任务系统接口总览](接口文档/任务系统/任务系统接口.md)为准，新增任务或工作流以[任务队列与工作流指南](角色文档/后端开发/任务队列与工作流指南.md)为准。

## 1. 系统边界

任务系统负责“可靠地投递、执行和观察后台任务”，不替代业务数据的长期存储，也不把 HTTP 入队成功当作业务完成。

```text
手工触发: Admin API -> Queue Manager -> Redis/Asynq -> Worker -> Handler
周期触发: Scheduler leader -> 周期配置 -> Queue Manager -> Redis/Asynq -> Worker
工作流:   trigger task -> workflow state -> DAG root -> node/shard -> terminal summary
历史链路: task terminal event -> Redis 有界缓冲 -> DB history sink -> 查询/清理
```

核心职责如下：

- API 提供任务投递、查询、暂停、恢复、重跑、删除和运行配置管理入口。
- Worker 消费逻辑队列，执行普通 handler 或工作流节点，并维护重试、超时和终态。
- Scheduler 通过 Redis leader 租约保证同一 `app_id` 只有一个实例投递周期任务。
- Redis 保存待执行任务、运行态、租约、去重键和近期终态，不承担永久历史职责。
- 数据库保存紧凑任务终态、工作流汇总和失败摘要；原始请求载荷、完整结果和诊断上下文仍以结构化日志与 Trace 为准。

## 3. 运行模式与部署拓扑

`run_mode` 是位掩码：API=`1`、Worker=`2`、Scheduler=`4`。命令行 `-mode` 优先于配置文件 `run_mode`；未显式配置时默认使用 `7`。

| run_mode | 组成 | 适用场景 | 明确不承担的职责 |
| --- | --- | --- | --- |
| `1` | API | 只提供管理入口 | 不消费任务、不注册周期任务 |
| `2` | Worker | 独立执行面 | 不提供 HTTP 接口、不投递周期任务 |
| `3` | API + Worker | 执行面带探针或小规模服务 | 不注册周期任务 |
| `4` | Scheduler | 独立调度面 | 不执行节点、不提供 HTTP 接口 |
| `5` | API + Scheduler | 推荐生产控制面 | 不执行任务节点 |
| `6` | Worker + Scheduler | 受控一体化执行面 | 不提供 HTTP 接口 |
| `7` | API + Worker + Scheduler | 本地联调或单实例环境 | 无角色拆分 |

生产推荐拆成两类进程：

```bash
# 控制面：管理接口 + 周期调度
./bin/admin -f ./etc/config.yaml -mode 5

# 执行面：按队列权重消费任务
./bin/admin -f ./etc/config.yaml -mode 2
```

扩容原则：

- API 按请求量扩容；Scheduler 可以多实例部署，但同一 `app_id` 只有 leader 实际投递。
- Worker 按队列积压、任务耗时和外部依赖容量扩容。增加 Worker 前先确认数据库、Redis、Kafka 和下游接口能承受更高并发。
- 控制面与执行面必须使用相同 `app_id`、任务 Redis、工作流定义和 active release，否则会出现“能投递但无人消费”或状态不可见。

## 4. 配置来源与生效边界

### 4.1 核心配置

| 配置 | 作用 | 变更注意事项 |
| --- | --- | --- |
| `task.enabled` | 是否初始化任务系统 | 启动期能力，变更后重启 |
| `task.redis` | 任务 Redis 连接 | 启动期连接，变更后重启 |
| `task.default_queue` | 工作流默认逻辑队列 | 核对 Worker `queues` 是否监听 |
| `task.concurrency` | 单 Worker 进程并发度 | 提高前评估 DB、Redis 和下游容量 |
| `task.queues` | 队列权重 | `strict_priority=false` 时按权重消费 |
| `task.default_retry` | 未覆盖任务的默认重试次数 | 业务 handler 仍需幂等 |
| `task.default_timeout_seconds` | 未覆盖任务的默认超时 | 超时不等于外部副作用自动回滚 |
| `task.completed_retention_seconds` | Redis 成功任务近期明细保留 | 允许范围由启动校验限制为 `0` 或 `600..7200` |
| `task.history.*` | 终态异步落库、保留期和缓冲边界 | DB 故障只影响历史可见性，不改变任务终态 |
| `task.scheduler.*` | leader 租约、同步、心跳和积压上限 | 仅 Scheduler 角色使用 |
| `workflows.*` | 工作流插件与运行参数 | 插件和 DAG 注册属于启动期能力 |

完整字段、默认值和重启边界见[配置字段说明](角色文档/后端开发/配置字段说明.md)。

### 4.2 周期配置来源

`runtime_config.source` 决定 `task_periodic` 的权威来源：

- `file`：从运行期文件读取，适合本地开发或尚未启用数据库发布的环境。
- `database`：从运行配置 active release 读取；运行期文件中的 `task_periodic` 只用于首次导入种子，不能继续作为线上修改入口。

周期项支持 `cron` 或 `every_seconds` 二选一，并可声明 `workflow`、`queue`、`targets`、`shard_total`、`gray_percent`、`retry`、`timeout_seconds`、`deadline`、`unique_key` 和 `unique_ttl_seconds`。发布前必须确认工作流已注册、队列可消费、分片与超时在业务允许范围内。

## 5. 多站点隔离

多个站点共用同一任务 Redis 时，`app_id` 是强制命名空间：

- 同一站点的 API、Worker、Scheduler 必须使用逐字节相同且非空的 `app_id`；发布清单应记录三个进程的实际值，任一不同即停止发布。
- 不同站点必须不同；值只能包含字母、数字、点、下划线或短横线。
- 系统按 `app_id` 隔离物理队列名、工作流状态、唯一键、Scheduler leader 锁和聚合分组。
- 管理页面显示逻辑队列名，不显示底层命名空间前缀。

不要通过手工拼物理队列前缀实现隔离，也不要让同一站点的控制面与执行面使用不同 `app_id`。

## 6. 队列与执行语义

默认逻辑队列：

| 队列 | 典型任务 | 使用原则 |
| --- | --- | --- |
| `critical` | 少量必须尽快完成的高优先级任务 | 控制流量，避免长任务占满高优先级 Worker |
| `default` | 普通后台任务 | 使用默认重试、超时和权重 |
| `maintenance` | 批量、归档、用户标签和维护任务 | 单独评估批次、并发和数据库压力 |

任务执行必须满足以下语义：

- 入队成功只代表 Redis 接受任务，不代表 Worker 已开始或业务已完成。
- 自动重试会重新调用 handler；涉及写库、发消息或调用外部接口时必须使用业务唯一键、状态机或幂等记录。
- 超时和进程退出可能发生在外部副作用之后，恢复逻辑不能假设“返回错误就没有写入”。
- 队列暂停只阻止该逻辑队列继续取任务，不会撤销 active 任务，也不会自动停止 Scheduler 投递。
- 人工重跑只适用于仍存在于 Asynq archived 集合的失败任务；已经清理的任务应使用业务补偿入口重新生成。

## 7. 工作流语义

普通任务对应一次 handler 执行；工作流通过 `workflow:trigger` 创建状态并按 DAG 推进节点和分片。

```text
trigger 入队
  -> Worker 创建 workflow 状态
  -> 调度根节点
  -> 节点/分片达到终态
  -> 依赖满足后推进后继节点
  -> 汇总 workflow 终态并异步写入历史
```

操作时需要区分：

- `taskId`：单个 Asynq 任务实例。
- `workflowId`：一次工作流执行实例，用于串联节点、分片和终态。
- `workflowName`：稳定工作流定义名称。
- `queue`：逻辑消费队列。

工作流失败后先定位首个失败节点和分片，再判断是重跑 archived 任务、重新触发完整工作流，还是执行领域补偿。不要只看最终汇总错误后直接释放锁或改数据库状态。

## 8. 状态与历史保留

### 8.1 Redis 实时态

Redis 保存 `pending`、`active`、`scheduled`、`retry`、`aggregating`、`archived` 和短期 `completed`。任务列表按状态选择主时间：

- `scheduled` 使用 `nextProcessAt`。
- `retry`、`archived` 优先使用 `lastFailedAt`。
- `completed` 使用 `completedAt`。
- `active` 使用 `startedAt`。

已知完整 `taskId` 时应先选队列并精确查询；模糊查询只覆盖受控的近期窗口，不能当作永久检索。

### 8.2 数据库终态历史

`task.history` 默认启用异步落库：

- 任务终态摘要默认保留 1 天。
- 工作流汇总默认保留 7 天。
- 最终失败摘要默认保留 14 天。
- Redis 待落库事件默认上限 2000，默认每 5 秒刷新，默认每 60 秒小批量清理过期历史。

保留期配置受启动校验约束；数据库故障时事件暂存在 Redis 有界缓冲，超过硬上限会裁剪旧事件并暴露降级状态。业务任务已经完成时，历史落库失败不能反向修改其业务结果。

## 9. 后台页面操作顺序

### 9.1 每日巡检

1. 打开“任务队列”，确认目标队列存在、Worker 在线、pending/active/retry/archived 没有异常增长。
2. 检查 `data.scheduler`：是否启用、是否为 leader、最近同步时间、心跳和入队错误。
3. 检查 Redis 容量、聚合降级提示和历史收集器 `status`、`pending`、`delaySeconds`、`lastError`。
4. 打开“任务列表”，按队列和状态查看近期失败；再查 DB 历史确认全部终态摘要。
5. 打开“工作流状态”，检查长时间运行或终态不一致的实例。
6. 打开“配置热加载”，确认 active release、当前生效版本和 `restartRequired`。

### 9.2 手工触发

1. 从任务注册表确认 task type 或 workflow name 已注册。
2. 选择能被 Worker 消费的逻辑队列。
3. 填写目标、分片、灰度、重试、超时和唯一键；生产批量任务先用小范围验证。
4. 记录返回的 `taskId`、`workflowId`、`workflowName` 和 `queue`。
5. 先观察入队和 active 状态，再按业务输出、数据库结果、日志与 Trace 验证完成语义。

### 9.3 暂停与恢复队列

暂停前记录目标队列、受影响 task type、active 数、允许完成窗口和恢复负责人。暂停后 active 任务仍会执行，Scheduler 也会继续投递；若目标是停止新增周期任务，必须禁用对应周期项、发布新的 active release，并确认下一触发时间已消失。恢复前记录 pending/retry/archived、平均耗时、现有 Worker 并发以及数据库、Redis、Kafka 和下游接口的延迟/错误率阈值。只有积压预计清空时间超出发布窗口且所有下游指标低于既定阈值时才逐级增加 Worker；每一级扩容后至少观察一个任务耗时窗口，错误率或依赖延迟超过阈值立即停止扩容并回退。

## 10. 周期任务未触发的判定顺序

周期任务只有同时满足以下条件才会入队：

1. `task.enabled=true`。
2. 当前进程 `run_mode` 包含 Scheduler 位 `4`。
3. `task.scheduler.enabled=true`。
4. 当前实例已取得同 `app_id` 下的 leader 租约。
5. active release 中存在目标周期项且 `enabled=true`，`workflow` 已注册，`queue` 被 Worker 监听，`cron` 或 `every_seconds` 恰有一个合法值。
6. `cron` 或 `every_seconds` 合法，目标工作流已注册。
7. 目标队列积压未达到 `max_queue_backlog`；未配置时使用安全上限 `10000`。
8. 唯一键和 TTL 没有抑制本次重复投递。

排查时按这个顺序核对，不要从 Worker 日志直接推断 Scheduler 故障。

## 11. 故障处置

### 11.1 队列持续积压

1. 按队列查看 pending、active、retry、耗时和错误分布。
2. 确认 Worker 在线、监听正确队列且与控制面使用同一 `app_id` 和 Redis。
3. 判断瓶颈是 Worker CPU、数据库慢查询、Redis、Kafka、对象存储还是外部接口。
4. 先降低或暂停新增周期投递，再根据下游容量调整 Worker 数或 `concurrency`。
5. 恢复后观察 retry/archived 是否继续增长，避免只消化 pending 而掩盖持续失败。

### 11.2 任务反复重试或进入 archived

1. 用 `taskId` 查询详情，记录 task type、queue、attempt、错误、Trace 和业务唯一键。
2. 从最外层 Worker 日志定位已包装的根因；不要只根据展示文案修改状态。
3. 判断 handler 是否幂等、外部副作用是否已经发生。
4. 根因消除且任务仍在 archived 时才能人工重跑；无法证明幂等时使用领域补偿流程。

### 11.3 工作流长期运行

1. 查询 `workflowId`，定位未终态的节点和分片。
2. 对照队列检查对应 `taskId` 是 pending、active、retry 还是已丢失。
3. 检查节点超时、Worker 心跳、Redis 租约和业务锁 owner。
4. 只有确认原执行者终止、外部副作用可判定且锁 owner 匹配时，才使用领域提供的精确释放能力。

### 11.4 历史不可见或延迟

1. 先确认 Redis 实时态，避免把历史落库故障误判为任务未执行。
2. 查看队列观测中的历史收集器状态、待落库数量、延迟、丢弃数和最近错误。
3. 检查数据库连接、目标表和清理任务；恢复后等待缓冲刷新。
4. 若缓冲已经裁剪，只能从结构化日志、Trace 和业务数据恢复证据，不能伪造历史记录。

用户标签专属锁、运行期表和 outbox 故障见[任务系统与用户标签排障手册](功能模块/用户标签/任务系统与用户标签排障手册.md)。

## 12. 发布与验收

上线或修改任务系统配置前，至少完成：

- 控制面和执行面分别记录实际 `run_mode`、`app_id`、任务 Redis 地址/DB/认证别名以及逻辑队列列表；API/Scheduler 与 Worker 的 `app_id`、Redis 目标和共享队列必须逐项相等，`run_mode` 则分别包含计划部署的 API/Worker/Scheduler 位。
- 目标工作流、task type 和 handler 已出现在注册表，周期项引用名称完全匹配。
- 新增任务的幂等、超时、重试、并发、锁 owner、终态和告警边界已验证。
- 任务历史表和相关迁移已执行；active release 已发布到目标环境。
- `GET /api/live`、`GET /api/ready`、任务队列、任务列表、工作流状态和配置热加载均可查询。
- 先用小目标或 `dryRun` 完成一次端到端验证，再放开正式批量或高频调度。
- 已准备禁用周期项、暂停队列、回滚代码和执行业务补偿的顺序与负责人。

仓库级验证至少运行：

```bash
make fmt-check
go test ./...
git diff --check
```

## 13. 常见误区

- “接口返回成功”不等于“任务执行完成”。
- “队列名相同”不代表两个站点共享任务；底层还受 `app_id` 隔离。
- “周期任务未运行”不一定是 Worker 故障，必须先查 Scheduler leader、active release 和唯一键。
- “配置热加载成功”不代表 Redis、数据库、路由、插件或 Worker 已重建；`restartRequired=true` 时必须重启。
- “completed 列表为空”不代表任务从未成功，它只覆盖短期 Redis 明细。
- “释放租约”不是通用恢复手段；必须先确认 owner、原执行者和外部副作用。
