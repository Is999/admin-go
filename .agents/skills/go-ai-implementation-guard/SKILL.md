# Go AI 实现防漂移

## 禁止用术语代替检查

- 说“闭环”时，必须列出生产入口、主调用链、成功与失败分支、最终副作用、注册/配置、同步面和验证；只有 helper、脚手架、DTO、单一分支或孤立测试时判定为未闭环。
- 说“简洁、清晰、可维护”时，必须逐个检查新增目录、接口、结构体、状态、分支、wrapper 和 helper 的当前调用方与职责；没有需求、调用方、稳定复用边界或故障证据的层级不得保留。
- 说“已同步”时，必须先从 route、request/response、RouteMeta、权限/安全、业务码/i18n、配置、Model、初始化 DDL/DML、SQL/Lua、Redis Key、前端契约、文档、测试和运维步骤中识别源码触发面，再记录每个触发面的依据、修改文件和验证结果；不得用汇总“不适用”代替未执行检查。
- 说“验证通过”时，必须给出最后一次修改后的命令、执行目录、范围和结果；旧快照、只测 helper、只编译或只跑 happy path 不算当前候选版本的完成证据。

## 执行流程

1. 确认 Git 根目录，读取生效的 `AGENTS.md`、AI 开发文档和 `references/project-map.md`。
2. 需求含糊、只要求分析、存在两个以上会改变实现文件或外部行为的合理解释，或将改变 API、数据、权限、安全、缓存兼容、迁移/补偿和用户可见流程时，先使用 `$requirement-intent-gate`。
3. 修改前追踪真实入口、调用链、数据契约、外部副作用和现有测试。
4. 非平凡任务先说明目标行为、源码依据、拟改文件、非目标和已确认假设。
5. 闭合完整生产路径，不只写 helper、脚手架或单一分支；交付前使用 `$implementation-closure-review`。
6. 保持改动小而聚焦，复用现有分层、helper、错误包装、logger、配置模式、资产加载器和测试风格。
7. 先检查成熟依赖或框架。新增抽象、目录、依赖或框架前，说明必要性、替代方案、影响范围和验证方式，并取得确认。
8. 按下方“实现判定清单”逐项复核结构、抽象、命名和中文注释，不能用一句“代码简洁、命名准确”替代逐项判断。
9. 最后一次修改后先运行每个改动文件的归属包测试；共享类型、helper、RouteSpec、配置、Model 或注册清单变化时，再运行所有直接调用包和 `go test ./...`。全量命令被数据库、Redis、外部服务或工具链阻塞时，记录原命令、第一处错误、未覆盖包，并运行全部可执行的归属包与直接调用包测试。

## 实现判定清单

### 入口与调用链

- 从 route、CLI、Worker、Scheduler、Collector、bootstrap spec 或运行时 registry 中确认真实入口，并追到 handler/consumer、logic/jobs、model/infra 和 response/output。新文件没有注册或调用方时判定为孤立实现。
- 对每个需求分支列出输入条件、状态变化、数据库/Redis/MQ/文件/外部服务副作用和最终输出；成功、校验失败、下游失败、超时/取消与重试终态均应有确定行为。
- 修改启动期组件时核对注册、配置、默认值、关闭顺序和重启边界；修改运行期参数时核对 normalize/getter、reload 应用器、回退行为和可观测状态。

### 结构与抽象

- Handler 只保留协议解析、参数校验、安全上下文和响应写出；业务编排进入 Logic/jobs，数据读写进入 Model/Repository，基础设施通过已有 ServiceContext/infra 注入。
- 只转发参数且不承担校验、转换、事务、重试、缓存、指标或外部依赖隔离的 wrapper 应内联；连续 wrapper/helper 跳转不能隐藏真实业务分支或副作用。
- 新增接口必须满足至少一项：已有两个及以上实现、隔离外部依赖、解除真实依赖环或提供测试替换点；只有一个具体实现且没有替换需求时保留具体类型。
- 新增 helper 必须收口已经稳定的重复规则，或明显缩短主流程；仅出现一次、只有一行转发或名字比逻辑更难理解时不提取。
- 锁、租约、事务、CAS、幂等、超时、取消、重试和状态机如果保护可复现的并发或故障窗口，属于正确性边界；不得为了减少代码行数删除。

### 命名与注释

- 目录、文件、变量、方法、常量、结构体、接口和字段名称必须对应当前业务对象或动作；职责变化时同步改名。`handleData`、`doProcess`、`CommonConfig`、`DefaultValue`、无领域限定的 `Manager/Helper/Info` 视为待复核泛名。
- 新增或重构的变量、常量、方法、结构体、字段、map 字段、路由、GORM Model、接口和关键逻辑必须有中文注释；新增或修改的项目自有 YAML 固定配置字段必须有紧邻字段上方、同缩进的中文注释。未导出、逻辑短、父节点已有概述或审计脚本未命中都不是省略理由。
- 注释至少说明一项代码无法自行表达的信息：业务意图、数据来源、key/value 语义、单位、排序/去重、空值、上限、并发、降级或风险。只重复标识符或写“处理数据、优化逻辑、兜底”视为无效注释。
- YAML 字段注释必须说明消费组件和用途；源码定义了枚举/范围/单位、缺省/空值/零值、normalize/getter、reload/restart、敏感信息或跨字段约束时逐项写明。动态 map 重复项只有在父字段已经定义 key/value、空值和合并语义时可不重复；第三方 schema、纯数据清单或生成文件必须记录路径、schema 所有者和排除依据。

### 改动范围与兼容

- 每个修改文件和关键 diff 必须映射到需求项、必要同步面或验证修复；无映射的重命名、格式化、目录移动和顺手重构移出本任务。
- 默认保持请求/响应字段、业务码、权限、安全策略、配置键、数据库/Redis 数据形状、错误、事务、时序和外部副作用；需要改变时列出旧行为、新行为、调用方、兼容窗口和清理条件。
- 不回滚用户已有改动，不用大范围重构掩盖局部问题。没有生产入口只能证明未启用；样例、兼容分支或未来占位只有经三分类确认不承载扩展契约、共享约定、测试、部署或运维能力后才可删除。

## 后端硬规则

- 使用项目指定 errors 包包装底层错误；`error` 级日志只放在 handler、worker、scheduler、startup、health 等最外层。
- MySQL 默认使用 GORM 链式调用；原生 SQL 说明必要性、索引、扫描范围、批量、超时、并发和 DB 压力。
- 随应用运行的原生 SQL 与 Redis Lua 分别保存为 `*.sql.tmpl` 和 `.lua`，通过 `go:embed` 加载并在执行前剥离文件头说明。
- DDL/DML 变更直接更新完整初始化基线，不新增碎片化迁移 SQL 或日常迁移版本；存量库本地 SQL 放在被忽略的 `data/sql-changes/<change-id>/`，只交付 DBA/运维执行。
- 修改 SQL 前评估执行计划、基数、返回行数、batch、cursor、timeout、concurrency 和目标库压力。
- 包装 `http.ResponseWriter` 时核对 `Flusher`、`Hijacker`、`Pusher`、`ReaderFrom`、`Unwrap`、Range、取消和真实写错误；无改写需求时直接透传，禁止无上限整包缓存下载或大响应。
- 除非需求明确改变契约，保持 YAML、API、权限、业务码、前端类型和文档行为稳定。

## 交付证据

逐项说明：

- 每个需求项对应的入口、调用链、实现文件和最终副作用。
- 每个源码触发面的依据、修改文件与验证结果；常见风险面若判定不适用，附具体证据；同时列出明确非目标。
- 最后一次修改后的验证命令、执行目录、结果和未覆盖路径。
- 当前状态属于已完成且已验证、已完成但未验证、已跳过、被阻塞还是交付待人工执行。
- 是否需要新库初始化、DBA/运维 SQL、回填、缓存失效、配置 reload、进程重启、回滚或补偿。
