# 数据库初始化与变更交付治理

## 1. 治理目标

本文定义 `admin-go` 数据库资产的唯一维护方式，解决需求迭代不断产生日期化、一次性和碎片化迁移 SQL 的问题。

项目采用“**仓库维护完整初始化基线，存量库变更由 DBA/运维在仓库外执行**”的治理模式：

- 仓库中的 DDL、DML 和迁移清单只用于创建全新空库，不承担已部署环境的逐版本升级。
- 每次需求涉及表、字段、索引或基线数据变化时，直接修改对应的原始初始化 SQL，使新环境一次初始化即可得到当前完整结构和基线数据。
- 面向现有环境的增量 DDL、DML、回填、修复和补偿 SQL 只生成在本地忽略目录，通过受控渠道交给 DBA/运维执行，不提交 Git，也不登记到项目迁移清单或 `schema_migrations`。
- 发布单、工单或 DBA 变更平台负责保存审批、文件摘要、执行记录和结果证据；代码仓库不充当一次性 SQL 的归档系统。

该规则适用于人工开发和 AI 生成的所有数据库变更。不得以“便于发布”“后续可能复用”或“先留模板”为由向仓库追加一次性迁移文件。

## 2. 资产边界

| 资产 | 是否进入仓库 | 维护位置 | 用途 |
| --- | --- | --- | --- |
| 完整建表 DDL | 是 | `internal/database/assets` 中对应原始 SQL | 仅用于新空库初始化 |
| 完整基线 DML/seed | 是 | 对应原始 seed SQL | 仅用于新空库写入当前基线数据 |
| 项目初始化清单 | 是 | `internal/database/migrations.go:defaultMigrationSpecs` | 只登记稳定初始化资产，不按需求追加版本 |
| 运行时代码 SQL | 是 | 稳定业务目录中的 `*.sql.tmpl`，由 `go:embed` 加载 | 应用真实运行能力，不属于数据库迁移 |
| 可复用运维工具 SQL | 是 | 已有 CLI、分表或部署工具的归属目录 | 必须有真实调用方、稳定输入、测试和长期维护责任，不得包装一次性需求 SQL |
| 存量库增量 DDL/DML | 否 | 本地 `data/sql-changes/<change-id>/` | 交付 DBA/运维命令行执行 |
| 一次性回填、修复或补偿 SQL | 否 | 本地 `data/sql-changes/<change-id>/` | 受控执行，执行后按工单留证 |
| 发布专用 SQL 模板、空白占位脚本 | 否 | 不创建 | 防止无意义模板长期堆积 |

`data/` 已由仓库 `.gitignore` 排除。本地 SQL 生成后应确认忽略规则生效：

```bash
git check-ignore -v data/sql-changes/<change-id>/10_ddl.sql
git status --short
```

如果文件出现在 `git status --short` 的未跟踪或暂存列表中，必须先移出仓库索引并修正存放位置，不能继续交付。

## 3. 仓库初始化基线维护

### 3.1 DDL 变化

新增表、字段、索引或约束时，直接修改目标表的原始 `CREATE TABLE` 资产：

1. 对齐 GORM Model 的表名、字段类型、长度、默认值、`NULL`、主键、唯一约束、普通索引、时间字段和软删除语义。
2. 修改现有初始化 SQL，使其描述当前版本完整结构；不要创建 `add_*`、`alter_*`、`sync_*`、`repair_*` 或带日期/版本号的新 SQL。
3. 保持 `defaultMigrationSpecs` 为初始化清单；需求变更不得追加新的迁移版本、名称或资产登记。
4. 更新 schema 渲染、Model/DDL 对齐、seed 顺序和相关数据库测试。

### 3.2 DML 和基线数据变化

新增权限、配置、角色关系或其它初始化数据时，直接更新对应原始 seed 资产：

- seed 显式维护自增主键 `id` 时，新记录按 `id` 递增顺序放置。
- 约束、默认值和关联关系必须与当前初始化 DDL 一致。
- 初始化 SQL 只表达“新库最终应有什么”，不保留从旧值演进到新值的过程。
- 存量环境需要的 `INSERT`、`UPDATE`、`DELETE` 另行生成本地 DBA 变更包，不能把增量语句混入项目初始化流程后用于线上升级。

### 3.3 初始化清单的职责

`cmd/migrate`、`defaultMigrationSpecs` 和 `schema_migrations` 继续保留，但只承担新空库初始化和初始化资产完整性校验：

- `schema_migrations` 记录的是初始化资产，不是业务版本升级流水。
- 修改原始初始化 SQL 后，已初始化旧库可能与新资产 checksum 不同；这是基线演进的自然结果，旧库不得再使用项目迁移命令尝试追平或登记。
- 禁止为了消除旧库 checksum 差异而新增更高版本迁移、手工修改 `schema_migrations` 或重放完整初始化 SQL。
- 新环境必须从当前代码版本的完整基线初始化，不应先执行旧版本基线再顺序升级。

## 4. 存量数据库变更流程

### 4.1 开发阶段

涉及 DDL 或 DML 的需求按以下顺序处理：

1. 确认目标数据库、表、数据量、现有索引、调用链、部署版本和兼容窗口。
2. 修改仓库内原始初始化 DDL/DML、Model、代码、文档和测试。
3. 以“当前部署版本的真实结构”到“目标结构”的差异生成本地 SQL，不能简单复制完整初始化资产。
4. 在安全测试库验证前置检查、执行 SQL、结果校验和补偿路径。
5. 将本地 SQL、执行顺序、SHA-256、影响评估和验证口径通过发布工单或受控文件渠道交给 DBA/运维。
6. 发布完成后只在工单或 DBA 平台留存执行证据；不把执行过的一次性 SQL 回填到仓库。

### 4.2 本地变更包

推荐把同一次数据库变更放在本地目录：

```text
data/sql-changes/<change-id>/
├── 00_precheck.sql
├── 10_ddl.sql
├── 20_dml.sql
├── 90_verify.sql
├── 99_compensate.sql
└── RUNBOOK.md
```

这只是本地组织约定，不是要求生成一套空白模板。只创建当前变更真实需要的文件：

- `00_precheck.sql`：确认库名、版本、目标表结构、关键数据状态和前置条件。
- `10_ddl.sql`：字段、索引、约束或表结构变化。
- `20_dml.sql`：有界、可审计的数据新增、更新或删除。
- `90_verify.sql`：结构、行数、重复值、空值、索引和业务口径校验。
- `99_compensate.sql`：可安全自动化的前向补偿；无法安全回退时在 `RUNBOOK.md` 明确只能通过备份恢复或二次变更处理。
- `RUNBOOK.md`：执行顺序、依赖版本、锁表风险、预计耗时、观察指标、停止条件和责任人。

禁止把密码、DSN、生产数据样本、访问令牌或用户隐私写进本地 SQL 和执行说明。

### 4.3 DBA/运维交付内容

一次完整交付至少包含：

| 项目 | 必填内容 |
| --- | --- |
| 变更标识 | 工单号、需求号或发布号 |
| 目标范围 | 环境、实例、数据库、表；禁止只写模糊服务名 |
| 版本前提 | 当前应用版本、目标应用版本和兼容顺序 |
| SQL 摘要 | 每个实际文件的 SHA-256、语句类型和执行顺序 |
| DDL 风险 | MySQL 版本、锁表/重建表风险、算法支持、预计耗时和磁盘余量 |
| DML 边界 | 索引条件、预计扫描/影响行数、batch、事务、超时、间隔和幂等方式 |
| 前置检查 | 备份或快照、只读检查、执行账号权限和低峰窗口 |
| 验证标准 | `SHOW CREATE TABLE`、索引、行数、业务抽样、日志和指标 |
| 停止条件 | 超时、锁等待、主从延迟、错误率、影响行数异常或校验失败 |
| 恢复方案 | 回滚、备份恢复或前向补偿的明确入口 |

只有 SQL 文本而没有目标、顺序、风险和验证说明，不算可执行交付。

## 5. 命令行执行规范

DBA/运维应使用受控账号和本机安全凭据文件，避免把密码直接放在命令行历史中：

```bash
sha256sum data/sql-changes/<change-id>/10_ddl.sql
mysql --defaults-extra-file=/secure/path/mysql-client.cnf \
  --database=<database_name> --show-warnings \
  < data/sql-changes/<change-id>/10_ddl.sql
```

执行前后都必须记录目标库：

```sql
SELECT DATABASE(), @@hostname, @@version;
```

不得使用 `--force` 跳过错误。任一语句失败时停止后续步骤，保留错误、已执行语句和时间点，由 DBA 按 RUNBOOK 判断继续、补偿或恢复。

## 6. DDL 安全要求

- 先核对 MySQL 版本、表大小、索引、外键、主从拓扑和当前写入压力，再选择在线 DDL 算法；不能假设所有变更都支持 `INSTANT` 或 `INPLACE`。
- 明确是否会复制表、长时间持有 metadata lock、增加临时磁盘、阻塞写入或放大主从延迟。
- 大表变更优先采用 DBA 已批准的在线变更工具和限速策略，不在应用 HTTP、Worker 或启动流程中执行 DDL。
- 删除字段、索引或表必须先证明应用已停止读写，经过至少一个兼容发布窗口后再执行。
- MySQL DDL 可能隐式提交，不能把事务回滚当作唯一恢复方式。

## 7. DML、回填与补偿要求

- `UPDATE`、`DELETE` 和回填必须使用可命中索引的确定性条件，并在执行前用同条件 `SELECT` 验证预计影响范围。
- 大数据量按主键游标或时间窗口分批；明确 `batch_size`、超时、间隔、最大并发、断点和重跑幂等性。
- 禁止无界全表更新、巨大单事务、深分页、超大 `IN/NOT IN` 或在 HTTP 请求中执行历史回填。
- 数据清理优先归档或软删除；不可逆删除必须有备份、审批和影响行数保护。
- 应用发布依赖数据状态时，明确“先 SQL 后代码”“先兼容代码后 SQL”或“扩展—回填—切换—清理”的真实顺序。

## 8. 新空库初始化

只有确认目标数据库为空且配置无误时，才允许使用项目初始化工具：

```bash
SELECT DATABASE();
SHOW TABLES;
```

```bash
make migrate-status MIGRATE_CONFIG=./etc/config.yaml
make migrate-dry-run MIGRATE_CONFIG=./etc/config.yaml
make migrate-bootstrap MIGRATE_CONFIG=./etc/config.yaml
make migrate-status MIGRATE_CONFIG=./etc/config.yaml
```

`migrate-bootstrap` 会执行当前完整初始化资产并登记初始化 checksum。它不能用于升级已有环境、修复结构漂移或补齐新增 seed。目标库非空、来源不明或存在业务数据时必须停止，改走 DBA/运维存量库变更流程。

## 9. 禁止事项

- 禁止提交按需求、日期、工单或版本拆分的增量迁移 SQL。
- 禁止向 `defaultMigrationSpecs` 追加日常 DDL/DML 变更。
- 禁止把 `data/sql-changes`、DBA 执行包或生产 SQL 样本强制加入 Git。
- 禁止把存量库修复语句混入原始初始化资产后直接对线上执行完整文件。
- 禁止用 GORM `AutoMigrate`、启动期 schema 探测或业务请求动态改表代替 DBA 变更。
- 禁止为未来可能使用的回滚、修复或 seed 创建空白 SQL 模板。
- 禁止修改或伪造 `schema_migrations` 来掩盖 checksum 差异。

## 10. 交付检查清单

- [ ] 仓库只修改了完整初始化 DDL/DML，没有新增碎片化迁移 SQL 或迁移版本。
- [ ] Model、原始 DDL、基线 DML、代码、文档和测试已经同步。
- [ ] 本地增量 SQL 位于被忽略的 `data/sql-changes/<change-id>/`，未进入 Git 状态和暂存区。
- [ ] DBA/运维已收到实际需要的 SQL、SHA-256、目标范围、执行顺序、风险、验证和恢复说明。
- [ ] 大表 DDL/DML 已说明锁、扫描、批量、超时、并发、主从延迟和停止条件。
- [ ] 已明确新空库初始化与存量库人工变更是两条独立路径。
- [ ] 最终交付说明明确是否需要 DBA 执行、代码发布顺序、缓存失效、重启、回滚或补偿。
