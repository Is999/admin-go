# 前端权限码与 admin_permission 映射说明

## 适用范围

- `admin`
- `admin-vue`
- 前端、测试、联调同学

## 核心结论

- 前端真正用于鉴权的是后端 `/api/auth/codes` 返回的权限码字符串数组。
- 这些权限码字符串来自 `admin_permission.uuid`，不是 `admin_permission.module`。
- 前端路由 `meta.authority`、按钮 `v-access`、表格操作列 `auth`，最终都拿这个 `uuid` 字符串做匹配。

## `roles` / `roleIds` / `accessCodes` 的职责边界

### `roles`

- 表示当前账号启用角色的名称列表
- 主要用于前端布局展示，以及 Vben 路由过滤需要传入的 `roles`
- 不要用 `roles` 直接推断按钮、表格操作列或接口权限

### `roleIds`

- 表示当前账号启用角色的 ID 列表
- 主要用于识别特殊角色身份，例如当前项目约定角色 ID `1` 为超级管理员
- 不直接作为页面按钮显隐匹配值使用

### `accessCodes`

- 表示后端 `/api/auth/codes` 返回的权限码字符串数组
- 实际内容来源于 `admin_permission.uuid`
- 前端页面、按钮、表格和运行时权限判断都应优先使用它

### 当前项目推荐理解

- `roles`：给 Vben 路由过滤和展示层使用
- `roleIds`：给身份判定使用，例如超级管理员识别
- `accessCodes`：给真正的前端权限显隐与运行时判断使用

## 后端返回链路

### 角色权限如何变成 `/auth/codes`

1. 角色与权限的绑定关系，管理后台仍然保存的是权限 `id`
2. 后端从管理员角色关系、角色状态和角色权限关系缓存合并当前账号的有效权限 `id`
3. 后端通过共享的启用权限 `id -> admin_permission.uuid` 索引转换权限码
4. `/api/auth/codes` 把这些 `uuid` 作为 `string[]` 返回给前端

管理员换角色时失效该管理员的角色关系缓存；角色授权变更时失效对应角色的权限关系缓存；权限状态、`uuid` 或 `module` 变更时失效共享权限索引。路由鉴权与 `/auth/codes` 使用同一套角色状态和权限定义。

后台请求一次读取 `admin:session:{adminID}`，后续账号状态、强制改密、MFA、权限和请求上下文复用同一份会话；个人中心变更原子更新已有会话，字段异常时原子删除会话，Redis 更新失败时进入安全缓存阻断并补偿撤销会话，不回写旧状态。会话缺失按退出、撤销或过期返回 401。Redis 未初始化、读取失败或安全缓存正在补偿时返回 HTTP 503；只有尚未完成登录 MFA 且需要判断秘钥是否损坏时，才按管理员主键读取一次 MFA 秘钥。

### 代码位置

- 后端从权限表读取 `uuid`：
    - `internal/logic/rbac/admin_permission.go`
- 后端把 `uuid[]` 返回给前端：
    - `internal/logic/admin/admin.go`
- 后端把 `roles`、`roleIds`、`isSuperAdmin` 返回给前端：
    - `internal/logic/admin/admin.go`
- 前端请求权限码：
    - `apps/web-antd/src/api/core/auth.ts`
- 前端把权限码写入 `accessStore.accessCodes`：
    - `apps/web-antd/src/store/auth.ts`

## `uuid` 与 `module` 的职责

### `uuid`

- 面向前端权限显示与隐藏
- 必须和路由 `authority`、按钮 `v-access`、操作列 `auth` 保持一致
- 是 `/api/auth/codes` 的实际返回值

### `module`

- 面向后端接口权限模型
- 用于后端根据路由别名或接口模型控制是否允许访问
- 当前前端不直接用 `module` 做菜单、页面、按钮显隐判断

## 前端生效位置

### 路由权限

- 路由通过 `meta.authority` 配置页面权限码
- 路由守卫会把 `roles + accessCodes` 合并后交给 Vben 权限过滤
- 这里保留 `roles` 是为了满足 Vben 的过滤入参，不表示页面只按角色做鉴权
- 页面是否显示、按钮是否可见，仍然优先看 `accessCodes`

示例：

```ts
meta: {
  authority: [SYSTEM_ROUTE_PERMISSION_CODES.ADMIN_LIST],
}
```

### 按钮权限

- 按钮使用 `v-access`

示例：

```vue
<VbenButton v-access="[SYSTEM_ACTION_PERMISSION_CODES.ADMIN_ADD]">
  新增用户
</VbenButton>
```

### 表格操作列权限

- 操作列统一通过 `auth` 字段控制

示例：

```ts
options: [
  { code: 'edit', text: '编辑', auth: SYSTEM_ACTION_PERMISSION_CODES.ADMIN_UPDATE },
]
```

### 文档站权限码

后台接口文档入口使用 `OPS_ROUTE_PERMISSION_CODES.API_DOCS`（`200029`），前台 API 文档入口使用 `OPS_ROUTE_PERMISSION_CODES.API_SERVICE_DOCS`（`200068`）。入口仍属于 `admin_permission` 正常路由权限；具体 Markdown 资源由 `admin_doc_permission` 按 `site + path` 精确授权，不需要前端按钮常量。

| uuid | module | 用途 |
| --- | --- | --- |
| `200029` | `docs.index` | 后台接口文档页面入口 |
| `200068` | `docs.api_service.index` | 前台 API 文档页面入口 |

单篇文档权限键由 `admin_doc_permission.site` 与 `path` 组成，例如 `admin + 接口文档/后台系统/权限管理接口.md`、`api + 接口文档/前台系统/系统接口.md`。角色新增、编辑抽屉只维护基础资料；角色列表的权限配置弹窗使用“路由权限 / 文档权限”双页签，分别提交 `routePermissionIds` 与 `docPermissionIds`，后端会自动补齐对应文档站入口路由。只有查询权限的账号可只读查看双页签，拥有 `role.permission.update` 后才允许勾选和保存。访问时单篇 Markdown 只匹配自身资源，不做目录继承。

## 新增权限时的推荐步骤

1. 后端新增或确认 `admin_permission.uuid`
2. 后端确认 `/api/auth/codes` 能返回该 `uuid`
3. 在前端全局权限中心补充对应常量
4. 页面路由使用 `meta.authority`
5. 按钮使用 `v-access`
6. 表格操作列使用 `auth`
7. 联调时先检查 `/api/auth/codes` 是否包含该权限码

## 与老项目 vue-vben-admin 的对应关系

### 老项目

- 集中权限枚举：`PermissionsEnum`
- 路由权限字段：`meta.uniqId`
- 按钮权限：`v-auth` / `hasPermission`

### 当前项目

- 集中权限常量：`permission-codes.ts`
- 路由权限字段：`meta.authority`
- 按钮权限：`v-access`

## 联调排查建议

- 页面看不到：
    - 先检查路由 `authority` 是否和后端 `uuid` 一致
    - 再检查 `/api/auth/codes` 是否包含该值
- 超级管理员页面看不到：
    - 先检查 `/api/auth/profile` 是否返回 `isSuperAdmin=true` 或 `roleIds` 包含 `1`
    - 再检查前端是否已将超级管理员兜底后的权限码写入 `accessStore.accessCodes`
- 按钮看不到：
    - 检查 `v-access` 或 `auth` 是否引用了错误常量
- 后端接口能调但前端不显示：
    - 大概率是前端没有使用正确的 `uuid`
- 前端权限管理页面录入时：
    - `uuid` 负责前端权限显示
    - `module` 负责后端接口权限模型
- 排查职责混用时：
    - `roles` 只用于名称展示和 Vben 路由入参
    - `roleIds` 只看身份判定
    - `accessCodes` 才是最终权限显隐依据
