# 实现闭环复核

## 闭环通过条件

“闭环”不是代码已经存在，而是同一需求项同时满足：

- 有真实生产入口和注册点，能够从 route、CLI、Worker、Scheduler、Collector 或运行时 registry 到达新实现。
- 主调用链已追到数据库、Redis、MQ、文件、外部服务或最终响应，成功、校验失败、下游失败、超时/取消和重试终态都有确定行为。
- 参数、权限/安全、事务、幂等、并发上限、资源释放、可观测性和恢复路径按真实故障模型处理；不适用项有源码依据。
- 受影响的契约、配置、Model/初始化 SQL、缓存、前端、文档、测试和运维步骤已记录修改文件或不适用依据。
- 受影响的项目自有 YAML 固定字段具有紧邻且同缩进的中文注释，字段用途、取值/空值、生效方式和安全约束与配置源码一致；动态 map 与第三方 schema 的共享说明或排除依据已记录。
- 最后一次修改后的适用验证已通过；无法执行的检查明确标记未验证，不能把替代性静态检查写成生产验证。
- 交付状态与事实一致：待 DBA 执行 SQL、待发布、待清缓存或待重启属于“交付待人工执行”，不是“已上线”。

## 执行流程

1. 根据用户最新要求、已确认边界和修改前源码事实还原真实需求。
2. 为每个可独立验收的需求项建立闭环复核记录：入口与调用链、实现文件、被触发的同步面、验证证据和剩余风险。
3. 端到端追踪 route、middleware、handler/worker、logic、model/infra 和 response/output；生产入口未接通时，不能凭 helper、DTO、UI 壳或孤立测试声称完成。
4. 生产入口未接通不自动等于代码无用。仍提供稳定扩展契约、已有多实现入口、外部依赖隔离、跨服务共享约定或 CLI/Make/测试/运维能力，且职责、测试和接入边界明确时，记录为“基础能力/未激活”；保留该能力，但不计入生产闭环。
5. 单独检查 download、Range、SSE、长轮询、批量和大响应等协议边界；普通 JSON 测试不能替代这些路径。
6. 核对仓库实际存在且受影响的 API、业务逻辑、数据、配置、SQL/Lua、Redis、权限、安全、前端、文档、测试与运维面；不存在的面标记不适用。配置面逐字段核对 config struct/tag、默认值、normalize/getter、校验器、消费方、reload/restart 与 YAML 同缩进行级注释，不能以父节点概述或 YAML 可解析代替。
7. 涉及 DDL/DML 时，确认仓库只更新完整初始化基线、没有新增日常迁移版本或碎片化 SQL；存量库本地 SQL 被忽略且已形成 DBA/运维执行、验证和恢复闭环。
8. 复核目录、文件、变量、方法、常量、结构体、接口和字段是否匹配当前业务职责；新增接口必须存在外部依赖、真实替换点、依赖环或多个实现，新增 helper 必须收口稳定重复规则或显著缩短主流程，只转发参数且无独立职责的 wrapper 应内联。
9. 拒绝脚手架、样例、单一分支、happy path、未接线和未验证实现冒充完成；无法闭环时说明阻塞、影响和下一步。
10. 确认验证来自最后一次修改后的同一候选快照；worktree 与 index 结果不能混用。

## 命名原则

- 使用短而准确的领域名，避免 `handleData`、`doProcess`、`DefaultValue`、`CommonConfig`、`Manager`、`Helper`、`Info` 等泛名。
- 职责变化时同步改名；只有真实替换点才抽接口，不创建 catch-all 目录。
- 新增抽象、目录、框架或依赖前，确认成熟方案、必要性、替代方案、维护成本和开发确认结果。

## 闭环复核记录

以下字段是每个需求项都需要的完成证据，因此保持固定；`同步面` 的内部内容按源码影响动态展开，不要求为仓库不存在或未触发的技术面制造空字段。

```text
需求项:
确认依据:
入口/调用链:
实现文件:
同步面:
验证:
状态: completed-and-verified | completed-unverified | handoff-pending | skipped | blocked
说明:
```

`同步面` 先从代码、API/业务码/权限/安全、配置、Model/初始化 DDL/DML、SQL/Lua、Redis、前端、文档、测试和运维步骤中识别实际触发项，再逐项记录源码依据与修改文件；只有常见风险面可能被误判时才写不适用及具体证据。`验证` 必须写命令、目录、范围、结果和候选快照。禁止填写“相关内容已同步”“测试正常”。

目标仓库或同步面不清时，读取 `references/repo-surfaces.md`。
