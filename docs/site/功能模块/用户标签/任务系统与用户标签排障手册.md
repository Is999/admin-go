# 任务系统与用户标签故障处置手册

本文用于处理任务未触发、队列积压、工作流卡住、用户标签 full 租约、运行期表和事件 outbox 异常。它给出取证顺序、判定依据、安全处置和恢复验证，不替代字段级接口文档。

任务系统运行原理见[任务系统运行与操作手册](功能模块/任务系统/任务系统使用手册.md)，用户标签验收见[用户标签操作与验收手册](功能模块/用户标签/用户标签操作手册.md)，实现与数据边界见[用户标签架构与扩展指南](功能模块/用户标签/用户标签实现与调度说明.md)。

## 1. 处置原则

1. **先止损，再恢复。** 高速重复投递、数据库过载或下游异常时，先禁用周期项或暂停目标队列，避免扩大影响。
2. **先取证，再改状态。** 保存配置版本、`app_id`、`taskId`、`workflowId`、队列、节点、分片、Trace、错误和时间范围。
3. **区分控制面与执行面。** Scheduler 决定是否投递，Worker 决定是否执行，DB history 决定是否长期可见；三者故障不能互相代替。
4. **只使用精确恢复入口。** 不执行 Redis `KEYS`、无界 `SCAN`、通配删除，不手工修改工作流汇总或 outbox 为成功。
5. **保护幂等与 owner。** 重跑、释放租约或补偿前，先确认原执行者已经停止、外部副作用是否发生以及 owner 是否匹配。

## 2. 首轮取证清单

收到故障后先收集：

| 类别 | 证据 |
| --- | --- |
| 环境 | 服务版本、分支、环境、`app_id`、配置版本、active release ID |
| 进程 | API/Worker/Scheduler 实例、`run_mode`、启动时间、最近重启 |
| 任务 | task type、`taskId`、queue、status、attempt、scheduled/retry/timeout 时间 |
| 工作流 | `workflowId`、workflow name、node、shard、首个失败节点、终态 |
| 依赖 | 任务 Redis、数据库、Kafka/对象存储/下游接口健康状态 |
| 可观测性 | `traceId`、最外层错误日志、队列指标、Scheduler 与 history health |
| 用户标签 | mode、dry-run、UID/tagTypes、租约 owner/TTL、outbox state/attempt |

不要在还没有 `app_id + queue + taskId/workflowId` 时直接搜索全量日志或 Redis；这通常会得到多个站点和多个实例的混合证据。

## 3. 快速定位流程

```text
接口是否返回入队回执？
  否 -> API 参数/权限/安全链/注册表/Redis
  是 -> trigger 是否在目标队列？
          否 -> app_id、Redis、去重、Scheduler/producer
          是 -> Worker 是否监听并在线？
                  否 -> run_mode、queues、版本、readiness
                  是 -> 是否进入 active/terminal？
                          否 -> 暂停、积压、scheduled/retry
                          是 -> 业务节点/依赖/历史落库/领域状态
```

## 4. 任务无法手工触发

### 现象

- 接口返回 workflow/task 未注册、参数非法、队列非法、重复任务或 Redis 错误。
- 没有 `taskId`/`workflowId` 回执。

### 检查

1. 在任务注册表确认目标 task type 或 workflow name 存在。
2. 确认当前 API 版本与 Worker 版本一致；仅部署 API 新版本会导致“能展示配置但 Worker 无 handler”。
3. 核对请求 mode、队列、分片、重试、超时、唯一键和领域必填参数。
4. 核对 API 与 Worker 的 `app_id` 和任务 Redis。
5. 检查默认 unique key 或显式 `uniqueKey` 是否仍在 TTL 内。
6. 查看 API 最外层错误日志和 Trace；安全链失败要先按业务码处理，不进入任务排查。

### 处置

- 参数或注册问题通过代码/配置发布修复，不在 Redis 中伪造任务。
- 合法重复请求被去重时，等待 TTL、使用新的业务唯一键，或确认旧任务终态后通过受控补偿入口触发。
- 任务 Redis 不可用时恢复依赖并重新触发；不要降级到全局 Redis 或本地内存队列。

## 5. 周期任务未触发

### 检查顺序

1. `task.enabled=true`。
2. 至少一个实例 `run_mode` 包含 Scheduler 位 `4`。
3. `task.scheduler.enabled=true`。
4. 队列页 `data.scheduler.enabled=true`，`leader` 非空，`lastHeartbeatAt` 未超过配置的 leader 失效窗口，`lastSyncAt` 晚于目标 active release 的发布时间。
5. active release 包含目标周期项，`enabled` 未关闭，workflow 名称已注册。
6. `cron` 或 `every_seconds` 合法，时区和下一次触发时间符合预期。
7. 目标队列积压低于 `max_queue_backlog`。
8. `unique_key/unique_ttl_seconds` 没有抑制本次投递。
9. Scheduler 与 Worker 使用相同 `app_id` 和任务 Redis。

### 安全处置

- leader 不稳定时先检查 Redis 延迟、时钟和续约间隔，不要让多个实例强行跳过租约。
- active release 错误时创建并发布修正版；不要只改数据库当前行而绕过发布审计。
- 积压触发背压时先消化积压或降低频率，不要直接无限提高 `max_queue_backlog`。

## 6. 队列持续积压

### 判定

同时观察 pending 增长率、active 数、平均耗时、retry/archived 增长和 Worker 数。只有 pending 高但持续下降，可能是可恢复峰值；pending 与 retry 同时增长通常是依赖或实现故障。

### 处置步骤

1. 先禁用产生洪峰的周期项并发布 active release；如果 pending 在连续两个观察窗口仍增长，或 retry/archived、数据库锁等待、Redis 延迟、Kafka lag 任一超过既定告警阈值，再暂停目标队列。暂停前记录 active 数和允许完成窗口，不中断已进入不可回滚副作用阶段的任务。
2. 按 task type 和错误分组，找到最大流量和首个错误来源。
3. 查看 DB 慢查询、锁等待、连接池，Redis 延迟，Kafka lag 和外部接口限流。
4. 评估 handler 幂等后决定是否清理明显无效的 scheduled/retry，删除操作必须限定具体任务 ID。
5. 只有下游容量允许时才增加 Worker 或 `concurrency`；恢复时分阶段扩容。
6. pending 清空后继续观察 retry/archived 和下游错误，确认生产速率不再高于消费速率。

### 禁止操作

- 直接对任务 Redis 执行 `FLUSHDB`、通配删除或重建共享队列。
- 在未知副作用状态时批量“立即执行” archived 任务。
- 只提高 Worker 并发而不评估数据库和下游容量。

## 7. 任务反复重试或 archived

1. 用完整 `taskId` 查询详情，记录 attempt、last error、timeout 和 Trace。
2. 定位最外层 Worker 错误；区分瞬时依赖错误、永久参数错误、数据冲突和代码缺陷。
3. 查询业务数据判断副作用是否已提交。事务提交超时、HTTP 超时或进程退出都可能发生在对方已处理之后。
4. 修复根因并证明 handler 幂等后，才对仍在 archived 的精确任务执行重跑。
5. 若任务已不在 archived，使用领域补偿入口重新生成任务，并使用新的可追踪唯一键。
6. 对永久错误应停止自动重试、修正输入或进入 dead/人工处理，不要制造无限 retry。

## 8. 工作流长期运行或不推进

### 检查

1. 查询 `workflowId`，定位首个未终态节点和分片。
2. 查对应任务是 pending、active、scheduled、retry、archived 还是已经不存在。
3. 确认依赖节点的成功/失败计数和汇总状态一致。
4. 查看 Worker 心跳、节点显式超时、业务锁、租约和外部依赖。
5. 检查工作流历史是否只是 DB 落库延迟；Redis 实时态仍是运行判定源。

### 恢复

- pending：恢复监听该队列的 Worker或解除队列暂停。
- retry：修复根因并等待或精确重跑 archived 任务。
- active 但 Worker 已失联：等待租约/超时收口，确认副作用后使用领域恢复能力。
- 节点已终态但 DAG 未推进：保留状态快照，检查工作流计数与推进脚本；不要手工把汇总改成成功。

## 9. 历史页面缺失或延迟

### 判定

任务实时态在 Redis，短期终态和工作流汇总异步落库。历史不可见不等于任务未执行。

### 检查与处置

1. 在任务队列查看 history health：enabled、status、pending、pendingBytes、delaySeconds、dropped、lastError。
2. 用任务 Redis 实时态和结构化日志确认真实任务终态。
3. 检查历史表迁移、数据库连接和写入错误；恢复后等待默认刷新周期。
4. 缓冲达到硬上限时旧事件可能被裁剪。裁剪后只能用业务数据、日志和 Trace 重建事件证据，不能反写伪造历史。
5. 若清理过快，按容量和审计需求调整受控保留天数，不能把 Redis completed 当永久历史。

## 10. 用户标签工作流未触发

按以下顺序检查：

1. `workflows.user_tag.enabled=true`，并确认 Worker 已在修改后重启。
2. 任务注册表包含四个主工作流和两个维护工作流。
3. Worker 监听 `maintenance`，与 API 使用相同 `app_id` 和任务 Redis。
4. 当前版本只允许 `dryRun=true`；非 dry-run 会失败关闭。
5. `targeted` 同时提供 UID 和标签类型，`recalculate` 提供标签类型，`full` 不携带两者。
6. 周期触发时核对 active release 中 targets 固定包含 `dry_run=1`。
7. 查看 unique key 是否阻止完全相同的重复触发。

## 11. 通用用户标签节点没有结果

`collect_scope`、`evaluate_tags`、`resolve_changes`、`persist_results` 当前是明确的骨架阶段，dry-run 返回 `Skipped=true` 属于预期。判定方式：

- 工作流状态应按依赖顺序推进并成功终态。
- 正式 `user_tag` 结果不应变化。
- 日志应明确记录骨架跳过，而不是悄悄返回空成功。

如果需求是产生真实标签结果，这不是排障问题，而是尚未完成的功能开发；必须按[用户标签架构与扩展指南](功能模块/用户标签/用户标签实现与调度说明.md)实现业务阶段和生产闭环。

## 12. full 工作流被租约阻塞

### 12.1 先确认 owner

full 租约 owner 是 `workflowId|mode`。先查询：

- 当前 Redis owner 和剩余 TTL。
- owner 对应 workflow 的节点与终态。
- 是否仍有 active Worker、`finalize` 或 `dispatch_hooks`。
- workflow final-done 标记是否存在。

### 12.2 可以人工释放的条件

只有原 workflow 已失败或终止、没有运行节点、不在切表/派发窗口、请求 owner 与 Redis 精确匹配时，才能调用 `POST /api/user-tags/workflow-lease/release`。请求必须填写可审计原因，系统强制 MFA 时还需二次票据。

### 12.3 不可释放的情况

- owner 指向另一个 workflow。
- 仍有节点 active 或 Worker 状态未知。
- 正在 `finalize`，临时表与正式表状态未判定。
- 正在 `dispatch_hooks`，事件是否派发无法确认。

这些情况应先隔离 Worker、判定数据库和 outbox 状态，再设计补偿；禁止直接删除 Redis key。

## 13. 用户标签表结构缺失

### 现象

`prepare`、运行期清理或 outbox 任务报 table not found/column not found/index 相关错误。

### 检查

1. 新环境查询 `schema_migrations` 确认初始化基线；已有环境核对 DBA/运维变更单、执行记录和当前真实表结构。
2. 核对当前分支：主线、Proxy、应用分表的表资产不能混用。
3. 对照 GORM Model 检查 `user_tag_0`、`user_tag_0_tmp`、`user_tag_runtime_uid`、`user_tag_runtime_checkpoint`、`user_tag_event_outbox`。
4. 核对关键索引是否存在，尤其是 workflow/state/shard/next retry 的查询路径。

### 处置

- 全新空库按初始化治理执行 bootstrap；已有库由开发生成本地差异 SQL，经评审后交给 DBA/运维执行，文件不得进入 Git 或项目迁移清单。
- 不在运行中临时创建“差不多”的表；本地增量 DDL 必须以当前分支完整初始化资产、目标环境真实结构和 GORM Model 为依据。
- 执行后重跑聚焦测试和低风险工作流，核对 `SHOW CREATE TABLE`、索引与 Model，避免只补出表名却仍存在字段或索引漂移。

## 14. `dispatch_hooks` 被跳过或失败

### 被跳过

`workflows.user_tag.event_hook_enabled=false` 时跳过是预期。若 outbox 本身为空，启用 hook 也可能没有派发数量。

### 启用后失败

1. 确认 hook registry 已注册真实消费者。
2. 查看 outbox `workflow_id/event_id/state/attempt/next_retry_at/locked_by/last_error`。
3. 检查消费者是否以 `event_id` 幂等，是否存在下游限流或永久参数错误。
4. 未注册 hook 且存在事件时应返回错误并保留 retry，不能手工改 done。

## 15. outbox 长时间 running、retry 或 dead

### `running` 超过 15 分钟

- 说明领取 Worker 可能异常退出。`user_tag.event_outbox.retry_scan` 会恢复为 `retry`。
- 若没有恢复，检查维护 workflow 是否启用、Redis 扫描互斥锁是否长期被占用以及 DB 更新是否命中相同 workflow/shard 范围。

### `retry` 持续增长

- 按 `last_error` 分组，先修复 hook 或下游依赖。
- 检查 `next_retry_at` 是否到期、任务队列是否消费、批次是否过大。
- 不要通过缩短重试间隔制造下游风暴。

### `dead` 出现

- 单事件累计尝试达到 6 次进入 dead，属于需要人工判定的永久失败。
- 核对业务结果已经提交、事件是否被下游部分处理、`event_id` 幂等是否可靠。
- 修复数据或消费者后，通过受控补偿重新生成/重派；保留原 dead 行作为审计证据，不能直接重置全部 dead。

## 16. 恢复后验证

故障解除后必须完成：

1. 原因已经停止，不再产生新的 retry/archived/dead。
2. pending 持续下降，active 和处理耗时恢复到基线。
3. Scheduler `leader` 非空且租约未过期，`lastHeartbeatAt` 连续推进，`lastSyncAt` 已覆盖当前 active release，目标周期项的下一次触发时间晚于当前时间且符合 cron/every 与时区计算。
4. 历史收集器 pending/延迟回落，`lastError` 清除或已记录剩余影响。
5. 用户标签 workflow 进入正确终态，full 租约 owner 和 TTL 符合预期。
6. outbox 的 pending/running/retry/dead 数量与补偿记录一致。
7. 使用小范围或 dry-run 重新执行一条代表性链路，并核对业务数据、日志和 Trace。

## 17. 复盘与交接

复盘至少记录：影响时间、站点、任务/工作流范围、根因、为何现有防线未提前发现、止损动作、数据影响、补偿、永久修复、监控改进和负责人。交接说明必须明确是否需要继续禁用周期项、暂停队列、重启进程、执行迁移、回填数据、重派事件或回滚版本。
