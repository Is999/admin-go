# 用户标签架构与扩展指南

本文是用户标签模块的开发权威文档，说明插件装配、工作流拓扑、运行参数、表与分片、租约、事件 outbox、扩展位置和生产验收要求。当前代码只提供通用骨架和可靠性边界，不内置任何具体标签规则或业务清洗 SQL。

操作与验收步骤见[用户标签操作与验收手册](功能模块/用户标签/用户标签操作手册.md)，接口字段见[用户标签接口总览](接口文档/用户标签/用户标签接口.md)，故障处置见[任务系统与用户标签排障手册](功能模块/用户标签/任务系统与用户标签排障手册.md)。

## 1. 设计目标与边界

用户标签骨架解决四类稳定问题：

1. 把全量、增量、指定用户和指定标签计算收敛到同一 DAG 语义。
2. 通过固定 UID 桶和工作流分片控制批量扫描与并发。
3. 通过 full 互斥租约和 finalize 边界保护结果版本切换。
4. 通过事务内 outbox 和独立重派任务可靠投递标签 gain/lost 事件。

骨架层不应出现登录、充值、投注、返水等业务节点，也不维护业务事实表。具体业务接入必须实现通用阶段的稳定接口，并补齐口径、索引、批量、幂等、回填和回滚；不能为了某一条标签规则修改 DAG 拓扑。

## 2. 代码组织与装配链

```text
internal/jobs/plugins.go:UserTagPlugin
  -> internal/jobs/usertag/task.Plugin
  -> 注册 task handlers
  -> 注册四类主 workflow definitions
  -> 注册 runtime cleanup / outbox retry workflows
  -> internal/jobs/usertag/workflow.Service
  -> stage + repository + hook registry
```

| 目录 | 职责 |
| --- | --- |
| `internal/jobs/usertag/task` | workflow/task 名称、DAG 定义、handler 注册、维护任务和终态租约回收 |
| `internal/jobs/usertag/options` | 默认值、上限、targets 解析和运行参数归一化 |
| `internal/jobs/usertag/workflow` | 节点执行编排、上下文创建和阶段选择 |
| `internal/jobs/usertag/stage` | `prepare/finalize/dispatch_hooks` 通用实现及业务阶段骨架 |
| `internal/jobs/usertag/repository` | 运行期 UID、checkpoint、结果表、租约和 outbox 数据访问 |
| `internal/jobs/usertag/route` | UID 固定桶、工作分片与结果表路由 |
| `internal/jobs/usertag/hook` | 标签得失事件消费者注册和派发 |
| `internal/model` | 结果、运行期和 outbox 的 GORM Model 与表名 |

新增能力必须沿此装配链接入。不要在 `main`、bootstrap 或 handler 中额外注册用户标签任务，也不要建立第二套 workflow 名称表。

## 3. 工作流与节点契约

### 3.1 主工作流

| 名称 | 模式 | 默认队列 | 分片 |
| --- | --- | --- | --- |
| `user_tag.full.rebuild` | `full` | `maintenance` | 主业务节点支持工作流分片 |
| `user_tag.delta.refresh` | `delta` | `maintenance` | 主业务节点支持工作流分片 |
| `user_tag.targeted.calc` | `targeted` | `maintenance` | 不按 workflow shard 拆分 |
| `user_tag.tag.recalculate` | `recalculate` | `maintenance` | 主业务节点支持工作流分片 |

四类主工作流共享 DAG：

```text
prepare
  -> collect_scope
  -> evaluate_tags
  -> resolve_changes
  -> persist_results
  -> finalize
  -> dispatch_hooks
```

| 节点 | TaskType | 稳定输入/输出职责 | 当前骨架行为 |
| --- | --- | --- | --- |
| `prepare` | `user_tag:prepare` | 清理本 workflow 运行态；full 准备临时结果边界 | dry-run 不执行正式切表写入 |
| `collect_scope` | `user_tag:collect_scope` | 产生候选 UID 集合并写运行期 UID 表 | 返回 `Skipped=true` |
| `evaluate_tags` | `user_tag:evaluate_tags` | 按规则版本评估候选用户 | 返回 `Skipped=true` |
| `resolve_changes` | `user_tag:resolve_changes` | 对比旧结果，生成 gain/lost 差异 | 返回 `Skipped=true` |
| `persist_results` | `user_tag:persist_results` | 原子写结果和事件 outbox | 返回 `Skipped=true` |
| `finalize` | `user_tag:finalize` | full 提交结果版本；非 full 完成阶段收口 | dry-run 不做正式切换 |
| `dispatch_hooks` | `user_tag:dispatch_hooks` | 按分片领取 outbox 并派发 hook | 未启用 hook 时跳过 |

主节点显式超时为 24 小时。full 的 `finalize` 设置 `MaxRetry=-1`，禁止工作流全局重试覆盖；切表类动作必须由阶段实现自行定义可证明的重试和恢复语义。

### 3.2 维护工作流

| 名称 | TaskType | 超时 | 职责 |
| --- | --- | --- | --- |
| `user_tag.runtime.cleanup` | `user_tag:runtime_cleanup` | 1 小时 | 小批清理过期 runtime UID、checkpoint 和 outbox 历史 |
| `user_tag.event_outbox.retry_scan` | `user_tag:event_outbox_retry` | 9 分钟 | 在 5 分钟 Redis 互斥锁内扫描所有分片、回收异常 running 并重派 |

维护工作流是独立单节点 DAG，不参与任何主工作流成败。新增维护动作时应先判断是否需要独立任务，而不是把清理逻辑塞进 `finalize` 延长主链路。

## 4. 参数模型与安全上限

`RuntimeOptions` 由请求字段、workflow targets 和 `workflows.user_tag` 默认值归一化得到。稳定约束：

- 模式仅允许 `full/delta/targeted/recalculate`。
- `full` 禁止 UID 和标签类型；`targeted` 必须同时包含 UID 与标签类型；`recalculate` 必须包含标签类型。
- UID、标签类型去重、过滤非正数并升序，确保默认 unique key 稳定。
- `filter_hash` 明确拒绝，用户标签不能依赖后台临时筛选集合。
- `shard_total` 受任务系统全局分片上限约束。
- `batch_size` 范围 `1..10000`，`worker_count` 范围 `1..64`。
- 默认值：`shard_total=1`、`batch_size=2000`、`worker_count=4`、`diff_batch_size=10000`、`event_batch_size=500`。
- 业务阶段实现前 `dry_run` 必须为 true，服务端失败关闭。

并发预算不能只看单字段。最坏并发近似为：

```text
Worker 实例数 × workflow shard_total × 节点内部 worker_count
```

正式实现前必须把该值与数据库连接池、单 SQL 扫描范围、Redis pipeline、hook 下游限流和单批超时一起评估。

## 5. UID 分片与表路由

### 5.1 固定逻辑桶

用户标签结果、runtime UID 和 outbox 都使用：

```go
shard_no = idgen.ShardNo(uid)
```

其固定桶数由 `idgen.ShardMod` 定义，并与 `user.shard_no` 完全一致。`default_shard_total` 只控制一次工作流拆成多少执行任务，不改变 UID 固定桶，也不决定 Proxy 的物理表数量。

### 5.2 工作分片

工作分片领取连续桶区间：

```text
start = floor(shard_index × 1024 / shard_total)
end   = floor((shard_index + 1) × 1024 / shard_total) - 1
```

示例：

- 2 分片：`0..511`、`512..1023`。
- 4 分片：`0..255`、`256..511`、`512..767`、`768..1023`。
- 非整除分片也使用连续范围，不改为取模。

连续桶范围能使用 `shard_no` 索引。禁止用 `shard_no % shard_total` 或裸 `uid % shard_total`，否则会破坏索引范围扫描、跨服务一致性和扩容语义。

### 5.3 结果表边界

- 主线逻辑结果表为 `user_tag`，历史基线资产从 `user_tag_0` 初始化。
- full 使用 `user_tag_0_tmp` 作为临时结果边界；正式阶段需要证明 prepare、写入、finalize 和回退的原子性。
- ShardingSphere-Proxy 与应用分表候选分支有各自物理表和路由规则，必须与 `api-go` 使用同名分支和同一配置。
- 业务逻辑不得散落字符串表名，统一使用 `internal/model/user_tag_route.go` 和目标分支路由 helper。

## 6. 数据表职责

| 表 | 关键维度 | 生命周期 |
| --- | --- | --- |
| `user_tag` / `user_tag_0` | `uid`、`tag_type`、`tag_source`、`shard_no` | 正式结果，保留策略由业务定义 |
| `user_tag_0_tmp` | 与正式结果一致 | full 构建临时版本，提交或失败回收 |
| `user_tag_runtime_uid` | `workflow_id`、UID、固定桶 | 当前工作流候选集合，完成后清理 |
| `user_tag_runtime_checkpoint` | workflow、node、shard、游标/状态 | 节点断点与进度，完成后清理 |
| `user_tag_event_outbox` | workflow、event、UID、tag、action、state | 可靠派发，按状态和时间小批清理 |

`user_tag_event_outbox` 保存 `workflow_id`、`event_id`、`uid`、`tag_type`、`tag_source`、`action`、`shard_no`、`state`、`attempt`、`next_retry_at`、`locked_at`、`locked_by`、`last_error` 和 `dispatched_at`。新增字段时必须同步 GORM Model、DDL、索引、清理、接口/运维文档和回滚方案。

## 7. full 租约与结果提交

full 模式使用 Redis 精确租约保护结果版本写入和切换。owner 由 `workflowId|mode` 构成，释放脚本必须同时校验 owner，不能无条件 `DEL`。

主要状态边界：

1. trigger/prepare 获取或确认 full 写租约。
2. 主 DAG 执行期间续持租约，非 full 模式不得释放 full owner。
3. `finalize` 完成结果版本提交并写 workflow final-done 标记。
4. 最终 `dispatch_hooks` 分片完成后释放租约。
5. 节点最终失败时，插件按 workflow mode 和 owner 精确释放，避免失败实例永久占锁。

人工释放只是异常恢复入口，必须先证明原 workflow 已终止且不在 finalize/hook 窗口。owner 不一致说明有其它执行者或状态证据冲突，应停止处置。

## 8. 事件 outbox 语义

### 8.1 状态机

```text
pending -> running -> done
              \-> retry -> running
                     \-> dead（累计尝试达到 6 次）
```

- 领取时只查询 `pending/retry` 且 `next_retry_at` 已到期的数据，并在事务内改为 `running`、写 `locked_at/locked_by`。
- 派发成功后改为 `done` 并写 `dispatched_at`。
- 派发失败后增加 `attempt`、记录 `last_error` 和下次重试时间；累计尝试达到 6 次进入 `dead`。
- `running` 超过 15 分钟视为 Worker 异常退出，由 retry scan 恢复为 `retry`。
- 已成功事件保留 7 天，dead 保留 30 天，长期 pending/retry/running 超过 7 天按维护策略回收。

### 8.2 一致性要求

正式 `persist_results` 实现必须在同一数据库事务内写标签结果和 outbox。hook 以 `event_id` 做幂等，不能依赖“只调用一次”。标签提交事务失败时不得留下可派发事件；事件派发失败不能回滚已提交的标签结果，而应保留 retry/dead 证据。

`event_hook_enabled=false` 时 `dispatch_hooks` 跳过属于预期。开关为 true 且存在待派发事件时，没有注册 hook 必须返回错误，禁止把事件误标为 done。

## 9. 业务阶段扩展方法

### 9.1 `collect_scope`

实现前明确：

- 候选来源是全量 user 表、CDC 增量、指定 UID，还是稳定业务变更表。
- 查询必须命中 `shard_no` 与游标索引，并有 batch、deadline 和最大扫描范围。
- 写 `user_tag_runtime_uid` 使用幂等唯一键，重试不能重复扩张集合。
- 不允许把前端筛选 hash、Redis 临时集合或无 TTL 的缓存当长期事实源。

### 9.2 `evaluate_tags`

必须定义标签规则版本、输入字段、空值、时区、金额单位、状态过滤和依赖。规则变更需要可回放和可审计，不能只写在 handler 分支里。大表聚合优先通过已有统计表、CDC 清洗或离线预聚合，禁止在在线 Worker 中发起无边界关联查询。

### 9.3 `resolve_changes`

明确 gain、lost、unchanged 的比较口径和重复标签处理。按 UID 固定桶和有界批次读取新旧结果，输出稳定排序；若结果量可能很大，应落中间表或流式处理，不能把整站标签装入内存。

### 9.4 `persist_results`

- 结果写入、旧结果处理和 outbox 必须有明确事务边界。
- 唯一键要能承受节点重试和工作流补跑。
- 分片间不能更新同一行；确有冲突时先调整分区责任，而不是依赖最后写入获胜。
- SQL 优先使用 GORM 链式调用；确需原生 SQL 时使用嵌入 `*.sql.tmpl`，说明索引、扫描范围、批次、超时、并发和 DB 压力。

### 9.5 `finalize` 与回退

正式开放 full 前必须设计并演练：

- 临时结果完整性检查和抽样口径。
- 结果版本提交的原子步骤。
- finalize 进程崩溃后的状态判定。
- 旧结果保留时间与一键回退方式。
- 租约、final-done 标记、数据库版本和对外读路径不一致时的恢复顺序。

## 10. 调度与发布

运行配置 active release 可维护 `user_tag.delta.refresh`、`user_tag.runtime.cleanup` 和 `user_tag.event_outbox.retry_scan`。默认种子必须显式 `enabled=false`；delta 骨架种子固定携带 `dry_run=1`，业务阶段未闭环前不得移除。

周期项生效同时依赖：

- `task.enabled=true`。
- 运行进程的 `run_mode` 包含 Scheduler 位 `4`，`task.scheduler.enabled=true`，当前实例持有同 `app_id` 的未过期 leader 租约且续租时间持续推进。
- `workflows.user_tag.enabled=true` 且 Worker 已重启完成注册。
- active release 中 workflow 名称已注册，队列被 Worker 监听，targets 非空且属于该 workflow，`shard_total`、batch 和 timeout 位于服务端硬上限内。
- `maintenance` 队列未达到积压上限。

## 11. 测试与验收要求

修改用户标签模块至少覆盖：

- workflow 定义：名称、依赖、分片、超时和 finalize 重试覆盖。
- options：模式、UID/标签归一化、上限和 `dry_run` 失败关闭。
- 分片：固定桶、连续范围和跨分支表路由。
- 租约：owner 匹配、续约、终态释放和人工释放失败关闭。
- repository：GORM 生成 SQL、索引条件、批量上限和事务状态迁移。
- outbox：claim、done、retry、dead、running 回收、幂等和全部分片扫描。
- 端到端：trigger、DAG 状态、正式结果不变和 full 二次触发。

建议聚焦验证：

```bash
go test ./internal/jobs/usertag/...
go test ./internal/task/...
go test ./internal/handler/usertag/... ./internal/logic/usertag/...
```

交付前仍需执行：

```bash
go test ./...
git diff --check
```

## 12. 生产接入清单

- 标签定义、规则版本、数据源和口径已经评审并可追溯。
- 所有大表查询有索引、执行计划、批量、超时、并发和压力结论。
- 正式结果与 outbox 的事务、唯一键和重试幂等已验证。
- full 切换、旧表回退、租约恢复和补偿任务已演练。
- `shard_total × worker_count × Worker 实例数` 不超过数据库和下游容量。
- 周期项先灰度、小批、dry-run，再按证据逐步开放。
- 指标覆盖节点耗时、失败、积压、outbox retry/dead、租约和最终结果量。
- 接口、配置、SQL、Model、测试、运维手册和回滚说明同步完成。
