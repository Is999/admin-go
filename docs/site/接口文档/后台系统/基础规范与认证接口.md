# 基础规范与认证接口

本文档覆盖 admin 后台系统管理接口的基础规范与认证部分，接口风格参考 laravel-admin，统一返回：

```json
{
  "status": true,
  "code": 1,
  "message": "操作成功",
  "data": {}
}
```

## 鉴权

除登录接口外，后台系统接口均需要请求头：

| 请求头 | 必填 | 说明 |
| --- | --- | --- |
| `Authorization` | 是 | `Bearer <token>` |
| `Accept-Language` | 否 | 前端当前语言 |
| `X-Trace-Id` | 否 | 链路追踪 ID |
| `X-Timestamp` | 开启签名后是 | 秒级 Unix 时间戳 |

### 获取验证码

#### 请求示例

```http
GET /api/auth/captcha
```

#### 响应示例

```json
{
  "status": true,
  "code": 1,
  "message": "查询成功",
  "data": {
    "key": "captcha_xxx",
    "image": "data:image/gif;base64,...",
    "expireSeconds": 300
  }
}
```

#### data 内部字段

| 字段 | 类型 | 是否必须 | 默认值 | 字段解释 |
|------|------|----------|--------|----------|
| key | string | 是 |  | 验证码缓存 key |
| image | string | 是 |  | 120×44 的循环 GIF Base64 图片；包含 12 帧、每帧 180ms；4 个字符以不同相位上下跳动，并按每 3 帧一个字符的节奏从左到右逐个隐藏；两条错位移动的彩虹波浪带各含 3 条完全不透明的彩色线，另有 1 条横跨图片并上下摆动的单像素彩虹正弦线；线条扫过时覆盖字符像素，移开后的帧重新显示原字符；前景雪花和彩色曲线同样直接编码进图片像素 |
| expireSeconds | int | 是 | 300 | 验证码有效期秒数 |

### 登录

`POST /api/auth/login`

请求：

```json
{
  "username": "admin",
  "password": "123456",
  "key": "captcha_xxx",
  "captcha": "AB23"
}
```

验证码由登录接口单次消费；系统不提供绕过验证码并签发普通会话的账号预校验入口。MFA 绑定在登录后的受限认证流程内完成。

响应 `data`：

```json
{
  "token": "jwt-token",
  "user": {
    "id": 1,
    "username": "admin",
    "realName": "管理员",
    "needResetPassword": 0,
    "mfaStatus": 0,
    "existMFA": false,
    "buildMFAURL": "otpauth://totp/...",
    "forceMFAEnabled": true,
    "mfaBindRequired": true,
    "mfaCheck": 1,
    "frequency": 120
  }
}
```

### 业务码约定（与登录相关）

| 业务码 | 含义 | 说明 |
| --- | --- | --- |
| `6` | 需要校验 MFA 动态码 | 已启用账号的登录态 MFA 校验 |
| `5` | 需要先绑定并启用 MFA | 当前登录需要 MFA，且账号未启用或没有可用 MFA 秘钥时返回，用于区分“绑定”与“仅校验动态码” |
| `7` | 需要先修改登录密码 | `needResetPassword=1` 时优先引导改密 |
| `8` | MFA 校验已过期，需要重新验证 | 敏感操作的二次校验票据失效 |
| `50001` | 核心依赖不可用 | 鉴权依赖发生非 Redis 故障时返回 HTTP 503 |
| `50003` | Redis 不可用 | Redis 未初始化或读取失败时返回 HTTP 503；不应清理本地登录状态后自动重试 |

### 登录态初始化

`GET /api/auth/profile`

响应 `data` 包含当前管理员资料：`userId`、`username`、`realName`、`email`、`phone`、`avatar`、`roles`、`token` 等。

### 内网管理员自举

`POST /internal/auth/init-admin-bootstrap`

- 该接口仅用于首次上线或运维兜底时重置既有超级管理员账号。
- 免 JWT，但只注册到独立内网监听器，并校验私网来源、Ops 令牌、HMAC、时间窗口和 Redis nonce。
- 不允许新建账号，也不允许修改目标账号角色。
- 成功后会确保目标账号处于“首次登录状态”，可先改密，再继续绑定 MFA。
- 数据库重置已提交但登录态、权限缓存或 MFA 运行态清理失败时仍返回成功业务码，并以 `data.syncPending=true` 表示后台正在自动补偿缓存清理。
- 详细说明见 [内网初始化管理员接口](接口文档/后台系统/内网初始化管理员接口.md)。

### 权限码

`GET /api/auth/codes`

响应 `data` 为当前用户拥有的权限标识数组，例如：

```json
["admin.list", "role.list", "permission.list"]
```

### 刷新与退出

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/auth/refresh` | 当前有效会话主动续签访问令牌 |
| `POST` | `/api/auth/logout` | 退出登录 |

`/api/auth/refresh` 仍要求当前 JWT 未过期，并且 token 是 Redis 会话中的当前 token，或处于 30 秒刷新并发宽限期的上一枚 token。它不是独立 refresh token，也不能用于 401 后恢复登录态；401 客户端必须重新认证。

后台前端会在 JWT 生命周期达到约 80% 后主动调用该接口，并合并同一时刻的并发续签请求；接口成功后才使用新 token 发送后续业务请求。

### 健康检查

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/live` | 存活检查，不访问外部依赖 |
| `GET` | `/api/ready` | 就绪检查，探测 MySQL / Redis / Kafka / TaskQueue / Collector / CDC；Worker、Scheduler 模式同时校验对应运行态 |
| `GET` | `/api/metrics` | Prometheus 指标抓取入口 |

- 公开探活接口，不要求 JWT。
- 容器 `livenessProbe` 使用 `/api/live`，`readinessProbe` 使用 `/api/ready`。
- Prometheus 使用 `/api/metrics` 抓取指标，不要求 JWT。
- 访问日志默认被白名单屏蔽，探针高频访问时不会刷出 access log。
- 联调时应以响应状态和响应体为准，不要以“日志是否出现”作为可用性判断依据。

## 签名与加密

后端支持 `X-App-Id`、`X-Trace-Id`、`X-Timestamp`、`X-Signature`、`X-Crypto`、`X-Cipher`，并在版本化秘钥模式下额外支持 `X-Key-Version`、`X-Gray-Key`。后台接口是否执行签名验签、加密解密，统一由路由安全策略和秘钥管理中的有效版本决定，不再通过 `sys_config` 全局开关短路。`signStatus` 与 `cryptoStatus` 独立生效，允许只启用签名或只启用加密。

| 请求头 | 说明 |
| --- | --- |
| `X-App-Id` | `base64(appID)`，后端按 `secret_key.uuid` 查找密钥 |
| `X-Trace-Id` | 请求追踪 ID，参与签名和防重放；开启签名后必填，前后端必须保持同一值 |
| `X-Timestamp` | 秒级 Unix 时间戳，参与签名并校验 5 分钟时间窗口；开启签名后必填 |
| `X-Signature` | 签名方式：`A`=AES，`R`=RSA |
| `X-Crypto` | 加密方式：`A`=AES，`R`=RSA |
| `X-Cipher` | 字段级加密列表，值为 base64(JSON 字段数组)，不再支持 `cipher` 整包加密 |
| `X-Key-Version` | 可选，显式指定当前请求使用的秘钥版本；未传时按稳定/灰度规则选路 |
| `X-Gray-Key` | 可选，灰度分桶键；用于 `grayVersion + grayPercent` 的稳定路由 |

### 签名规则

AES/RSA 待签名字符串生成规则：

1. 按签名字段路径 ASCII 排序，`user.phone` 这类点路径读取对应嵌套值。
2. 跳过不存在、`null`、空字符串字段。
3. 先拼接 `v2|app=<字节数>:<appID>|trace=<字节数>:<traceID>|timestamp=<字节数>:<timestamp>`。
4. 每个非空字段依次追加 `|field=<字段名字节数>:<字段名><字段值字节数>:<稳定字段值>`；长度统一按 UTF-8 字节计算，值内出现 `&`、`=`、`:` 等字符也不会改变边界。
5. 按 `X-Signature` 指定的 AES 或 RSA 方式生成 `sign` 字段。

其它 `X-Signature` 值直接拒绝，不做算法降级。

签名与加解密的最终实现约束：

1. 加密字段是动态的，由 `X-Cipher` 决定。
2. 签名字段是固定的，由路由安全策略决定，不能通过请求头动态改写。
3. 响应处理顺序固定为“先按 `X-Cipher` 解密，再按固定签名字段验签”。
4. 签名字段路径必须按 ASCII 排序；点路径只签对应叶子值，不对整个父对象签名。
5. 若签名字段值本身是对象或数组，前后端都必须使用递归稳定序列化：
   - 对象的每一层 key 都按字典序输出；
   - 数组保持原顺序；
   - 禁止直接依赖普通 `JSON.stringify` / `json.Marshal` 的默认对象遍历顺序参与签名。
6. 为降低跨端序列化差异风险，响应签名优先覆盖稳定标量字段或明确点路径，避免直接对复杂对象整体回签；所有 `ResponseCipher` 字段都必须先以明文包含在 `ResponseSign` 中。
7. 路由签名字段为显式空数组时，仍执行签名，只使用 `appID`、`traceID`、`timestamp` 三个基础字段；值为 `null` 时才表示未启用该方向的签名。

说明：

- `signStatus` 与 `cryptoStatus` 各自决定对应链路是否执行；同时启用时，前端固定按“先解密、后验签”处理。
- 调整某个接口的响应加密字段时，仍需同步维护组合模式下的响应签名字段路径，但该声明不会强制启用签名开关。
- 调整某个接口的签名字段，需要前后端同步更新该路由的固定安全策略，但不通过请求头动态协商。
- 当前完整路由安全策略以生成文件 `docs/site/route_security_manifest.json` 为准；后端测试会同时校验前端运行时清单，避免手写字段表漂移。

### 版本化秘钥选路

1. 若显式传入 `X-Key-Version`，后端优先使用该版本。
2. 未显式传版本时，默认命中 `secret_key.stable_version`。
3. 当 `gray_version` 非空且 `gray_percent > 0` 时，后端按 `X-Gray-Key` 做稳定分桶，命中灰度版本后会在响应头回写最终版本到 `X-Key-Version`。
4. 秘钥缓存拆分为 `secret_key_route:{uuid}` 与 `secret_key_aes:{uuid}:{keyVersion}` / `secret_key_rsa:{uuid}:{keyVersion}`，并通过 `secret_key_version:index:{uuid}` 精确索引版本材料缓存，避免轮换时整组缓存互相污染，也避免生产 Redis 使用前缀 `SCAN`。

## 统一响应字段说明

| 字段 | 类型 | 是否必须 | 默认值 | 字段解释 |
|------|------|----------|--------|----------|
| status | bool | 是 | false | 状态: true 成功, false 失败 |
| code | int | 是 | 1 | 业务状态码 |
| message | string | 否 |  | 消息 |
| data | object/array/null | 否 |  | 登录信息、权限码、健康检查状态或空对象 |
